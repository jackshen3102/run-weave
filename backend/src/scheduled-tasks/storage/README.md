# 定时任务数据库升级

定时任务使用独立 SQLite。当前数据库版本为 **2**，由 `PRAGMA user_version` 保存；
`scheduled_schema_migrations` 记录每步的版本、名称、SQL SHA-256 和执行时间。
迁移入口是 [migrations.ts](./migrations.ts)，由 `ScheduledTaskDatabase` 构造时调用，
成功后才交付 store、恢复运行并启动调度。

## 升级链

| 版本 | 迁移内容                                                                                                    |
| ---- | ----------------------------------------------------------------------------------------------------------- |
| 0    | 历史未编号数据库，或新建空库                                                                                |
| 1    | 建立表与索引；已有库必须匹配已知的初始表、列、索引和外键结构才能纳入版本管理                                |
| 2    | 为缺失字段的任务及历史配置快照写入 `misfirePolicy: { mode: "skip" }`；历史运行缺失的 `dispatch` 写为 `null` |

已有明确补跑策略或调度时间的记录原样保留。迁移不改任务 revision、下次安排、运行状态、
输出、幂等键或历史错误，不触发任务，也不伪造旧运行的调度时间。
`dispatch: null` 表示未记录调度信息（包含历史运行和手动运行）。
当前业务模型要求明确的 misfirePolicy 和 dispatch，不在读取时继续解释旧格式。
创建 API 必须提供策略；PATCH 省略策略仍是“不修改”的局部更新语义。

## 原子性与失败处理

全部待执行迁移、迁移历史与版本更新在一个 `BEGIN IMMEDIATE` 事务内完成。
并发启动由 SQLite 写锁串行化，后取得锁的实例重新读取版本；失败时整体回滚。
重复打开已升级数据库只核对版本和迁移历史，不重新改写数据。

版本高于当前支持范围、迁移历史或校验值不符、未知旧库结构、无效源数据或迁移执行失败，
都中止定时任务存储初始化。其 API 返回不可用，错误原因包含 `scheduled_tasks_schema_*`；
不会启动调度，也不会删除数据库重建。Backend 的其他能力按原有子系统隔离方式运行。

已执行的编号迁移不可修改，只能追加下一步。每次新增迁移同步更新当前版本，
并通过旧库升级与失败回滚验证。这里采用单向迁移，不维护旧业务模型或自动 down migration。
已经发布且没有版本检查的旧程序无法被新库主动阻止；部署时不能让它重新打开升级后的库。

## 验证

`pnpm scheduled-tasks:verify-runtime` 的 migrations 检查使用临时数据库和真实 SQLite worker，
覆盖空库并发打开、无版本旧库与版本 1 升级、已存在策略保留、重复打开、失败整体回滚后重试、
未来版本拒绝、迁移历史篡改、未知表结构及无效源记录拒绝。不使用安装态数据库。
