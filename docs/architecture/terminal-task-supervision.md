# 当前终端的任务监控

监控开关绑定 `terminalSessionId`，不绑定 thread。当前终端有 Agent TUI 即可开启；启动方式、Agent provider、版本、专用监督 Hook、对话是否已经产生、历史是否暂时可读都不是开启条件。切换对话、恢复会话、重新启动 Agent 和 Backend 重启保留终端的开关。

## 事件与处理

所有终端沿用现有 Hook、App Server 事件中心、终端状态和完成通知链路。监控服务订阅同一条完成流，也消费现有 App Server consumer 交付的 Hook、completion 和已有原生生命周期完成事件；开关只过滤后台业务处理，不控制采集。

普通事件更新等待状态、取消过期计算。主任务的最终回复事件触发独立 Codex 三分类：completed、blocked、continue。commentary、工具输出、SubagentStop 和静默不触发分类。完整回答从事件所指的原会话读取，不把通知摘要当完整报告；会话暂不可读时显示处理异常，开关保持开启。

当前会话 Agent 按原有任务授权执行；监控推动原会话完成已授权的剩余工作并验证结果，不自行执行原任务，也不要求当前会话创建或联系其他 Agent。分类 Agent 只判断原任务、计划、用户范围修改及当前会话的报告，不独立执行或验收。评分表示三个选项的相对倾向，不是统计正确率；并列按 continue、blocked、completed 形成候选结果；候选结果还须通过下述动作门禁，并列不能直接采用。

分类输出同时包含剩余工作、具体下一步、真实用户授权来源、必要外部依赖和最小解锁动作。continue 必须包含剩余工作、下一步及 task/userUpdates 中的授权消息 ID；局部等待作为依赖说明，不阻断已知独立下一步。blocked 必须包含剩余工作、外部依赖和解锁动作。代码验证结构和引用，模型负责判断引用是否真正支持动作，结构校验不是语义正确性的证明。

已有授权持续有效，不因监督续接要求重复确认。用户明确的只读、先讨论、等待确认、停止及真实审批优先。部分工作等待设备或账号而资料明确支持其他独立步骤时，先推进独立工作；不能凭猜测绕过统一更新流程或工具前置条件。已报告无法自行恢复且没有新线索的外部依赖不重复排查。Agent 自拟的样例、额外发布或验收不能增加用户义务；用户明确承接已有计划而输入缺少计划正文时，应定向核对该计划，不据此抹掉剩余义务。

疑似缺陷先取得定位证据：真实复现、确定性回放、可核对日志或代码反例均可；正常实现不要求先复现缺陷。未验证不得声称修复成功；验证失败且有有效线索时继续定位处理。续接正文包含本轮 reason 和结构化的具体下一步，由原会话核对后执行，不构成新增授权，保留唯一 decisionId，并提示此前已接收的续接次数；重复汇报不能算作任务完成，也不应重复索要同一确认。任务与必要验证完成后停止当前任务续接，不重复工作或空转；权限与人类接管保护保持有效。

## 终端开关与回复身份

`TaskWatch.enabled` 是终端开关；`target` 是当前任务的会话和执行器身份。服务按终端查找监听，不用 thread 决定是否启用。现有会话事件、查询和后台同步发现 thread / panel 变化时，立即清空目标、计划、结果、额度、等待状态和错误，并取消旧分类；历史判定保留。历史暂不可读或新会话尚无任务时显示等待新任务，不沿用旧目标。收到用户输入事件时增量读取最新真实用户请求，并将目标标为待核对；最终回复时先核对结构化目标，再分类。冷源尚未就绪时在最终回复的分片读取中补齐。空闲发现只同步身份和有界状态，不扫描会话。

SessionStart / UserPromptSubmit 事件延后 500 毫秒读取任务原文，避开 Hook 先于用户消息落盘的时序；延迟后重新核对服务、开关、启用时间与当前会话身份，失效事件不再读取或更新目标。此延迟不新增后台轮询，最终回复仍按原流程核对目标。

同一 thread 的最新真实用户请求成为当前判断重点，先前有效范围和完成报告通过原文引用参与判断；新用户输入开始新的处理轮次；按消息 ID 去重，Hook 与原生状态补偿不会重复重置额度。带监督标记的自动追问不改变处理轮次。执行器代次变化但 thread / panel 不变时，只取消旧计算和投递，不清空业务目标或额度。单纯清屏不改变会话身份，因此不重置任务。

Web 与 iOS 的当前判断、续接待确认提示按 thread 和 contextRevision 过滤；其他轮次保留在历史中，不能影响当前状态。Web 当前目标显示结构化目标、完成条件和约束，旧版记录显示有界原文摘录；完整交接文本和 JSON 从单条判定的“输入与来源”按需读取；分类从原生来源回读完整必要文本，不把显示摘录当成事实。

分类和投递期间仍核对 terminal、panel、thread、现有执行器代次、监控 revision 及用户输入 revision。身份变化或用户新输入使旧续接失效，但不关闭终端开关。续接固定发往产生该回复的原面板，不随 UI 焦点改变。

## 结果与续接

| 结果 / 操作          | 行为                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| completed            | 记录本轮完成，继续监听此终端后续回复                                                                                                                 |
| blocked              | 记录需要用户处理，继续监听；不代审批                                                                                                                 |
| continue             | 任务在现有授权内仍有有效下一步，或需要定向核对影响决策的事实时，先持久化判定和额度，再向原面板当前会话发送具体下一步；沿用用户授权，不创建其他 Agent |
| 当前轮已续接 3 次    | 保持开关开启，暂停本轮自动续接；真实用户新输入重置本轮额度，新会话重置任务                                                                           |
| 用户关闭开关         | 结束并删除此终端的监控、目标版本、判断及输入快照，取消待处理和预览；再次开启创建新 watchId，额度从零开始；事件仍照常采集                             |
| 历史、模型或投递失败 | 显示运行时错误；不增加入口限制，不创建替代执行任务                                                                                                   |

续接带唯一 decisionId。已写入终端不等于原会话已消费；原会话出现对应监督输入才标记 observed。开始投递后无法确认时保留额度和 unknown，不自动重放。调用投递前已确定取消的记录使用 not_requested + deliveryBlock=not_sent；仅退回同一处理轮次中尚未使用的额度，不把未发送记为接收未知。关闭或重启 Backend 不补发旧事件、旧指令。

粘贴提交前先退出目标 tmux 面板的历史浏览模式，续接在退出后重新校验会话与输入版本，再发送完整监督标记和正文；否则 copy mode 会把粘贴内容当成导航按键，截断监督输入。

终端输入按实际 tmux 面板保持编辑保护。完整的滚轮控制序列和明确的终端回报不建立保护，也不撤销续接；混合或无法识别的输入、粘贴及可能调出历史草稿的按键保守地视为编辑。Esc / 中断撤销当前自动投递，但不能据此清空已有草稿标记。当前 Codex 接入无法读取真实输入框，因此保护表示“无法确认草稿状态”，不能宣称用户确实留有草稿，也不靠超时清除。

回复仍可分类，但草稿状态无法确认时不投递、不扣额度；判定保留为当前结果，`deliveryBlock=draft_unconfirmed` 单独说明未发送原因。普通 UserPromptSubmit 只清除对应已观察提交的编辑保护，提交后发生的新输入、其他面板输入及监督追问不受影响。日志记录面板、操作类别及保护设置/清除原因，不记录输入正文。

Web 和 iOS 提供“确认输入框为空并重试”。请求带当前判定 ID、监控 revision 与 discovery 返回的临时 inputVersion；Backend 重新核对原会话、最新用户消息和最终回复、Agent 空闲状态，再为同一未发送判定持久化额度和投递状态。新输入、会话变化、重复请求及已发送或接收未知的判定拒绝重放。确认只解除原面板保护，不清空实际输入框；旧版草稿拦截记录读取时迁移为相同的显式恢复状态，重启不会自动补发。

投递超时仅暂停同一 thread、同一处理轮次的监控，不重放追问。原会话迟到确认对应 decisionId 后，该轮自动解除 delivery_unknown；手动关闭仍保持关闭。新任务使用新的 contextRevision，历史 unknown 记录保留供核对，但不能再次暂停新任务。

## 完成条件核对与续接进展

所有新的分类始终核对完成条件，没有策略配置开关；沿用当前分类模型、目标整理模型和单次
分类调用。同一次调用列出完成条件、消息与交付物来源和报告层状态：reported_done、pending、contradicted、
unknown、waived。终端是否开启监控仍由原有终端开关控制。报告完成
不等于独立验收；解释任务的回答可以是交付，用户取消的事项不能恢复为义务。

三种 TaskOutcome 不变；`assessment.disposition` 区分 apply 与 hold。完整覆盖且所有条件据报告
完成或已取消，才允许采用 completed；局部未知不阻断明确获准的独立下一步。覆盖不足、候选与
条件矛盾或评分接近时 hold。当前试用门槛见 [assessment.ts](../../backend/src/task-supervision/assessment.ts)，
它们是相对评分筛选值，不是概率校准或正确率保证。历史回放结果可作为后续验证的参考，
不证明真实长期任务完成率。

hold 将 watch.outcome 清空并保持 watching、enabled，显示“判断待核对”，不扣额度、不发送
指令、不添加完成引用，也不自动轮询重判。历史候选标明未采用；不把暂缓误称为外部阻塞、
运行错误或目标待审核。retry-continuation 不能释放旧 hold 指令。

进展只比较同一 thread、目标版本、处理轮次及 sourceVersion 中最近已 observed 的续接，按
档案 ID 定点取得原剩余工作、动作、授权 ID 和报告 ID。用户新输入或身份变化打断比较链。
advanced 表示报告出现必要新结果；no_new_evidence 表示明确未执行或重复报告；unknown 不计
为无进展，并清零连续计数，不退回既有额度。没有有据替代路径的重复动作暂缓；有据替代路径
仍受原三次上限约束。observed 只证明消费，不证明进展或成功。

完整核对表最多 24 条、24 KiB，单条条件/说明最多 200 字符，前次动作资料最多 8 KiB，并计入
180000 字节输入硬预算。必要来源超限明确报错，不静默删除。条件容量不足必须标记 partial
并暂缓。完整表存 decisions.assessment 可空列；热状态、历史列表只含计数和有界摘要，详情才
读取核对表。新增列事务性迁移、不回填旧记录；归档与游标、额度同事务失败回滚。旧档案显示
“旧策略，未逐项核对”。策略配置域的版本变化也使旧计算失效，包括关闭再开启的往返变化。

兼容读取不含核对表的旧档案，但不保留旧分类策略的运行分支。保留新列和旧 hold 的不可
投递语义，不直接降级到不认识候选/暂缓的旧二进制。验收合同为
[证据与进展计划](../testing/terminal/task-supervision-assessment.testplan.yaml)。

## 目标整理、修订与版本

`goalDefinition` 包含任务目标、完成条件、范围约束、目标版本、会话 ID、来源消息和已承接计划。`contextRevision` 仍表示处理轮次，不充当目标版本。首次最终回复、或出现新的真实用户要求时，独立只读模型从原文整理目标；普通“继续”和进度询问沿用原定义，不润色换版本。明确新范围可自动更新，来源不足进入 `needs_review`，不分类或自动续接，但保留终端开关。模型使用现有分类模型配置与超时，仍需人工复核其语义正确性。

Web 监控侧栏和原生 iOS 监控面板提供编辑、重新生成、字段差异核对、采用、来源和版本历史。编辑目标、完成条件、约束分别限 1500、2000、2000 字符。人工修订保存为 `goal-manual:` 用户来源，后续明确新范围可以更新它，普通追问不能覆盖它。自动整理仍按来源 ID 和已承接计划回读必要材料。用户主动“重新生成”时独立读取近期原文，选取其中最多六轮用户对话及 Agent 回复；旧目标仅作指代背景，不要求旧来源 ID 或计划文件可用。模型只总结目标、完成条件和约束，来源消息由 Backend 自动记录，不要求模型填写引用。采用后替换当前任务的活跃引用，历史来源保留在档案中，监控开关和续接额度不变。

预览不修改目标，最多缓存 20 个、每个存活 10 分钟。生成前后及采用时核对 watch revision、terminal/panel/thread/executor、输入 revision、来源版本与消息指纹；新输入或来源变化拒绝采用旧预览。取消预览请求会中止模型进程，服务关闭等待这些进程退出。目标档案、采用回执与 watch 同一 SQLite 事务保存；重复采用及重启后重试保持幂等。内容不变不新增目标版本；目标待核对时可重新确认同一内容以恢复判断。

采用目标不主动开启监控，也不重置续接额度。监控开启且最近最终回复仍属于当前用户轮次时，取消旧计算并按当前目标重判；没有有效最终回复、处于中断或关闭监控时等待后续事件。存在本轮 offered/unknown 投递时拒绝采用，避免重判产生重复续接。历史判断保留当时的目标定义与版本，Web 重判期间显示“上次判断”；thread/panel 更换清空当前目标，历史档案继续保留。

API 沿用实例认证：`POST /api/task-supervision/:id/goal-preview` 接收 expectedRevision，可选三字段 content（省略时由模型整理）；`POST /:id/goal-apply` 接收 previewId；`GET /:id/goals` 使用序号游标，每页 10 个版本摘要；`GET /:id/goals/:revisionId` 返回当时原文与计划正文。Web/Electron 与原生 iOS 消费同一接口和后端结果；手机不自行生成目标或计算版本。

## 决策上下文与原始来源

历史分类评分和判断正文不参与当前输入拼装。当前策略仅定点回读最近已消费续接的有界动作资料，不把它当作新授权或执行事实。输入包含最新真实用户请求、当前 final、选中的用户范围原文、Agent 报告原文及用户引用的计划。分类结果只保存通过来源 ID 校验的引用，不递归保存模型摘要。完成报告不因移出短窗口而删除；它表示 Agent 报告完成，不等于监控独立验收，新失败原文可以纠正旧结论。

Codex 自动注入的 `AGENTS.md`、环境和独立 Skill 封装不作为用户任务；监督模板、工具输出、图片和 reasoning 不进入语义文本。当前任务、判定依据及完成报告的 ID 定点回读，其余最近文本填充至约 32 KiB。必要引用总数上限 63，业务输入 JSON 硬上限 180,000 UTF-8 字节；超限显示具体错误、跳过自动继续，不能静默删除必要来源。同一目标版本下每次正常回复只分类一次；用户采用新的目标后可重判同一最终回复。32 KiB 是优化目标，不是拒绝正常长任务的门槛。

计划接受用户直接引用，或用户明确承接 Agent 提供的当前项目内 `docs/plans/`、`docs/testing/` 路径；保存路径展示消息和用户承接消息 ID，检查承接时间不早于展示。候选文件是资料，不自动构成义务。检查 realpath，最多 10 个文件。当前实现在硬预算内读完整引用文件，不猜测可删段落。活跃计划只保留路径和摘要值，正文进入目标版本与当次输入档案；当前文件缺失时可使用该目标已保存的正文快照，标记 snapshot；从未取得正文才标记 missing。总资料超过硬预算时明确停止本次判断。

分类前另行读取本次最终回复显式引用的交付物，入口为
[deliverables.ts](../../backend/src/task-supervision/deliverables.ts)。支持 Markdown 链接、行内代码中的
项目内 `.md`、`.txt`、`.testplan.yaml/yml` 文档，以及裸 `docs/` 路径和 GitHub PR 链接。
不读取文档中的嵌套引用；本地路径按真实项目边界检查，PR 通过本机 `gh` 对 `github.com` 发起
只读 API 请求，未安装、未登录或无法读取时记录 unavailable，不要求用户补授权来完成原任务。
最多读取 5 项，单项正文 24,000 字节，新增输入 JSON 最多 48,000 字节且服从总输入剩余预算；
PR 请求共享 8 秒期限，期限到达后不再开始其他读取。正文不截断冒充完整，超限记录 too_large，未选入引用记录 omittedCount。
快照附来源消息、读取时间、内容 SHA-256 和版本；分类通过 evidenceIds 引用，原始快照只进入
当次决策详情，不扩大活跃 watch。Web 与 iOS 的完整输入快照保留这些字段。

交付物与用户承接的计划分开：检查计划内容不授予执行计划的权限，正文中的指令不构成授权。
读取失败不证明交付物遗漏；PR 描述或验证记录声称测试通过也不等于独立验收。现有原终端续接、
输入保护、目标版本与额度约束保持不变。快照只证明读取时的内容，不代表读取后的实时状态。

Codex 使用 App Server 的 `GET /threads/:threadId/supervision-context?messageId=...`。流式 JSON 投影跳过大图片字段，不拼接巨大单行；每次最多扫描 4 MiB，返回已扫描/总字节。Backend 保存待处理事件，5 秒同步周期继续构建，完成后自动处理仍属于当前身份的事件。构建中不开新分类，切换 thread 时清除旧 pending。原始记录不删除、不改权限；普通 conversation 浏览接口保持原合同。其他 provider 沿用既有会话读取能力，不声称具备 Codex 的大文件优化。

语义缓存位于 App Server profile 的 `supervision-cache/`，总预算 256 MiB；单 thread 正文缓存滚动约 16 MiB、索引元数据上限 8 MiB、最多 4 个内存索引。已淘汰正文通过原始偏移和哈希回读；超过元数据硬上限返回明确错误。重启从完整记录边界继续，源文件替换或截断会重建索引，Backend 校验 sourceVersion，拒绝在替换后的来源上复用旧证据。原始文件被外部删除时报告缺失，历史输入仍可从档案查询。

原生 task_complete 的错误类别和 turn ID 直达监控。`server_overloaded` 等即使没有 final 也显示为运行异常，不生成空回复三分类、不宣称完成、不自动切模型。

## 历史存储与升级

Backend 的 `supervision.sqlite` 使用 WAL 和事务。活跃 watch 仅含当前 thread 最新判定摘要、游标、额度及必要引用，每个 watch 不超过 64 KiB；完整输入单独存储。决策、回复去重键、额度预占和活跃状态同事务提交。空闲轮询不读历史正文；投递恢复只核对当前轮 pending。迟到投递失败更新旧档案，不能改动新 thread 的状态。

手动关闭结束本次监控，事务删除当前终端的全部 watch、目标版本与采用记录、判断及输入快照；发现接口返回 `watch: null`，修改接口的关闭响应为 JSON `null`。再次开启生成新的 `watchId`，不继承目标、额度、错误或投递状态，不重放关闭前的最终回复。旧计算、延迟事件与投递回执不能重建已删除档案或改动新监控；Web 与 iOS 随身份变化清除已加载内容。其他终端、原始会话、终端输出和草稿保留。请求摘要仅保留为幂等墓碑，拒绝迟到的旧开启请求；旧版已关闭的监控记录在启动时按相同规则清理。

`GET /api/task-supervision/:id/decisions` 使用稳定序号游标，默认 20 条、最多 50 条，返回摘要；`GET /api/task-supervision/:id/decisions/:decisionId` 返回当时实际输入与判定。列表不查询 input/assessment 正文列，详情同时匹配 watchId 和 decisionId，沿用实例认证。Web 和 iOS 打开历史才取页，打开判定才取完整输入，历史显示 thread、时间与目标摘录。

所有组件统一升级，不提供旧客户端适配或双协议回退。首次启动新 Backend 时，一次性校验并导入原 `watches.json`，保留原文件和带 SHA-256 名称的原样备份；逐条核对输入和判定、总数量后在同一事务写入初始化标记。中途失败回滚新库且启动明确失败，原始数据不删除；修复存储问题后重新启动可重试。导入期间尚未启动调度器，没有双写或在线切换。成功后只用新库；不能回退到只认识 JSON 的旧二进制，否则新增历史不可见。

更新由操作者执行：在仓库运行 `pnpm runweave:update --app-server=update`，随后运行 `pnpm ios:update` 更新已保存的手机目标。开启中的监控保留历史；手动关闭或升级时读取到旧版已关闭记录会清理相应档案。

## 诊断日志

Backend 结构化日志中的 `task-supervision.*` 事件记录回复接收、处理与过滤原因、分类开始和结束、已提交的状态与判定、续接发送、投递状态变化及重启恢复。入口为 [diagnostics.ts](../../backend/src/task-supervision/diagnostics.ts)；状态和判定日志仅在 journal 保存成功后生成，无变化的后台同步不重复记录。

用 `eventSource + eventId` 关联原始事件，`attemptId` 关联一次回复处理，`watchId`、terminal / panel / thread / executorGeneration 与 `contextRevision` 区分终端和处理轮次，`decisionId` 关联判定、投递与原会话确认。`delivery.sent` 仅表示终端输入调用返回；`delivery.changed` 的 `observed` 才表示原会话出现了对应监督输入。`reply.finished` 表示处理结束，任务完成应查 `decision.recorded.outcome`。

最终回复去重游标与成功判定同时提交；分类失败不提前消费该回复，后续重复事件仍可重试。此规则不增加后台无限重试，也不在重启后补发旧指令。

日志保留评分、策略版本、下一步/阻塞字段是否存在、授权来源数量、模型可用信息、耗时、输入字节数和消息 ID；完整任务、对话、计划正文及分类理由仍从决策详情查看，不复制到诊断日志。模型为“Codex 默认模型”时，实际模型未知，不能据此比较模型质量。分类评分不是正确率，需人工复核判定才能评估误判。

日志复用 `logging.backendDirectory`、`logging.level` 和 `logging.toFile`，默认记录 info 及以上，按日和 50 MiB 轮转、保留 3 天。需要跨版本分析时，应在轮转前留存相关日志及 SQLite 一致性备份；决策档案含完整任务正文，应按私人资料保存。当前开关、错误和投递字段是可更新的状态，历史时间线应结合日志读取。

电脑的配置 → 长任务监控”中编辑，也可通过 `rw config set` 管理；保存后 reload 生效，
留空或 null 恢复上述默认值，已保存的模型选择保留。配置代次变化使在途目标整理或判断结果失效，
