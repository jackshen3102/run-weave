# Agent Race 第 2 轮代码审查

## 结论

通过 `AGT-REVIEW-GATE`。上一轮 `race_create_end_mutual_exclusion` P1 已按同一 review harness 独立确认修复；本轮未发现仍然开放的 P0/P1。

仍有 1 个非阻断 P2：显式删除 Race worktree 尚未复用创建屏障，可能与同一 Worker 的 Session 创建交错。该问题需要后续收敛，但不改变本轮 Code Review gate 结论。

## Resolved Findings

### P1（已解决）：创建与结束没有互斥，已结束的 Race 会被创建流程重新写回

- 位置：`backend/src/race/race-service.ts:162-165`、`backend/src/race/race-service.ts:203-208`、`backend/src/race/race-service.ts:353-370`
- 修复核对：`create()` 为当前创建建立 `creationSettled`，只在 `finally` 释放；`end()` 在读取最终记录、停止 Session 和清除 store 前等待该屏障。
- 同场景复验：
  1. 用内存 store 和可暂停的 `RaceWorktreeSupply.plan()` 实例化真实 `RaceService`。
  2. 启动 `create()`，等待初始 `starting` 记录写入。
  3. 调用 `end(raceId)` 并确认其在 plan 收敛前没有返回。
  4. 让 plan 以原场景的可控错误结束，再等待 create/end 全部完成。
- 结果：`endReturnedBeforePlanSettled=false`，写序列为 `["starting","failed","clear"]`，`finalRaceId=null`。上一轮“clear 后再次 write”的反例不再成立。
- RACE-010：DELETE 完成后记录保持 `null`，原 create 不再复活同一 Race。

## Remaining Findings

### P2：显式 Worktree 删除仍可与 Worker Session 创建交错

- 位置：`backend/src/race/race-service.ts:276-351`、`backend/src/race/race-service.ts:373-400`
- 风险：`removeWorktree()` 没有等待 `creationSettled`。当 create 已登记 worktree、但 `createSession()` 尚未返回时，另一客户端可以成功删除该 worktree；随后原 create 仍会回填新 Session ID并继续启动，最终留下指向已删除 worktree 的 failed Session，删除请求执行的 `beforeRemove` 因当时 Session ID 为空而无法停止它。
- 受控 harness 结果：删除完成时 `terminalSessionId=null`；释放暂停的 `createSession()` 后最终记录变为 `terminalSessionId="orphan-session"`，`destroyed=[]`，写序列显示 Session 在删除成功后才被回填。
- 严重度判断：该路径需要第二客户端在 POST 尚未完成时直接调用无 UI 的显式删除 API，且 Session ID 最终仍登记在 RaceRecord、可由结束 Race 清理，因此当前定为 P2，而不是阻断 RACE-010 修复的 P1。
- 修复方向：显式删除应复用同一创建屏障，或引入按 Race/Worker 的生命周期互斥；删除成功返回后不得再为该 Worker 创建或回填 Session。
