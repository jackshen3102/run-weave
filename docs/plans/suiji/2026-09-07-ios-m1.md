## 2. 连接、凭据与请求生命周期

SuijiSession 管理当前服务、认证与页面入口；APIClient 绑定一个不可变的服务端点。
地址规范化保留协议、主机、端口与有效路径语义，不能把不同路径的服务误判为同一个。
登录后取得并验证 serverId/ownerId；本地草稿和附件作用域为规范端点、serverId、ownerId 的组合。
serverId 变化不自动把旧草稿提交给新服务；需要用户明确选择后续处理，不做隐式迁移。

- token 存 Keychain，服务地址等非秘密偏好存 UserDefaults；正文和附件不放 UserDefaults。
- 参考现有 APIClient 的无 Cookie URLSession、刷新合并和连接代次检查，独立实现随记所需范围。
- 401 可恢复认证；明确无效才显示登录，网络错误保留身份与草稿。读请求认证恢复后最多自动重试一次。
- 写操作在发送前尽量刷新即将过期的凭据；401、超时或服务不可用之后，由用户再次操作，不自动重发业务请求。
- 切地址、退出登录时取消旧请求并更换代次；旧响应不得写入新连接的列表、凭据或草稿。
- 退出登录清除该 session 凭据并遮蔽私有页面；草稿留在原作用域，重新验证相同身份后恢复。
- M1 不做多账号管理 UI；设置只提供当前云地址、账号状态与退出入口。

刷新 token 的提交若响应丢失，可以要求重新登录恢复；不得把认证失败误报为记录已丢失。
与本地 Runweave 节点的登录、连接切换完全独立。

## 3. 本地草稿与保存结果

### 3.1 编辑中的草稿

DraftStore 使用串行写入与原子替换保存元数据，选中的附件先复制到 App 自有目录再引用。
正文、类型、原记录 ID/version、附件本地路径和上传状态形成一个可恢复的草稿。
每个身份保留一个新建草稿，以及按 recordID 区分的编辑草稿，不提前增加草稿列表产品。

自动保存本地草稿只涉及磁盘。只有原子写入成功后才显示“草稿已保存在本机”；写盘失败保留内存输入并提示，
不能以“已保存”提示让用户放心退出。可以短暂合并连续输入写入，但不能承诺进程在写入完成前被强杀也零丢失。
本次持久化确认后的内容必须能在进程重启后恢复。

收起编辑器保留草稿，再次进入恢复；明确“放弃草稿”才删除本地草稿文件，并在有内容时确认。
这里不删除任何服务器记录或附件。重新打开某条记录的编辑器时，先检查该记录草稿，不静默用远端正文覆盖。
纯附件草稿同样持久化；系统文件选择器的临时 URL 不作为永久来源。

### 3.2 用户按保存时

1. 校验当前限额和内容；正文不 trim 后回写，URL 保持普通正文。
2. 冻结本次提交快照，先把上传操作的幂等键及对应本地文件写入草稿，再逐个上传缺失附件。
3. 附件 ID 齐备后，把记录请求的操作、完整 payload、expectedVersion 与幂等键写入本地，再发送请求。
4. 只有收到有效的成功响应才显示“已保存”，应用服务器 ID/version；原子移除已确认的草稿和本地附件副本。
5. 提交期间冻结编辑与重复保存，仍允许安全收起页面；草稿不得在请求结束前被清除。

网络恢复、进入前台、重新登录或进程启动都不能自动上传、创建、编辑或改待办状态；可以恢复读取列表。
避免客户端使用宽泛的网络库重试策略，把写操作也随 GET 一起重放。

### 3.3 超时、冲突与重试

超时不能推断服务器没有提交。进入“保存结果待确认”状态，保留冻结请求和幂等键；
用户点“重试确认”发送完全相同的请求，服务返回原结果。重启后仍使用原键，不能根据正文生成新键。
未确认期间不能直接编辑或丢弃这次意图并另建记录，否则会制造不可解释的重复记录。
上传响应丢失也遵循相同规则；附件上传成功而记录失败时复用已有附件 ID，不重复生成逻辑附件。

明确的输入错误允许回到编辑；409 版本冲突保留草稿，读取最新版用于比较。
用户查看差异后才能选择基于最新版重新编辑或放弃本地修改；不能偷偷换 expectedVersion 强制覆盖。
已完成/不再做的记录仍可编辑正文；冲突处理不改变任务状态。

状态变更也保存一个带 expectedVersion 的待确认操作，并以相同幂等规则手动重试。
它不伪装为正文草稿；未确认时显示待确认标记，阻止同一记录发起第二个冲突写操作。

## 4. 原生视觉与组件

采用 SwiftUI 与 SF Symbols。SwiftUIX 补充框架缺失的控件能力，并不直接提供原型的整套视觉，M1 不引入。
原型的参考主题如下；尺寸转换为原生 points 后以真机阅读为准，不进行 HTML 像素逐项复刻。

| 元素            | 参考                                                     |
| --------------- | -------------------------------------------------------- |
| 主色 / 浅色底   | `#087B60` / `#E6F3EE`                                    |
| 页面底 / 分隔线 | `#F3F6F5` / `#E4EAE6`                                    |
| 正文 / 次要文字 | `#202B29` / `#74817B`                                    |
| 卡片            | 白底、约 16 圆角、细边框，外侧约 20 留白                 |
| 正文与时间      | 跟随语义字体与 Dynamic Type，参考正文 16、时间 12 的层次 |
| 新增入口        | 右下角约 54 的绿色按钮，避开底部导航与安全区             |

集中实现 RecordCard、FilterBar、TaskStatusBadge、AttachmentPreview、RecordEditorSheet、
CaptureButton、BottomNavigation 与 EmptyState。它们接受数据与动作；样式复用通过主题、ViewModifier、
ButtonStyle 解决，不把不同屏幕的业务状态都塞入通用组件。

- 记录流可用 ScrollView/LazyVStack 保留原型卡片节奏；导航用 NavigationStack。
- 筛选和底部导航可以自定义外观；保留原生可访问名称、选中状态和触控区域。
- 新增与编辑采用系统 sheet；编辑器处理焦点、滚动与键盘安全区，首页不自动 focus。
- 图片使用 PhotosPicker；Markdown 使用系统文件选择器。HEIC/HEIF 转为 JPEG 后再按限额检查并显示实际文件信息。
- 初版 Markdown 可安全显示原文；阅读体验需要格式化时再评估专用渲染库，不执行 HTML 或请求远程嵌入图片。
- 下载图片与 Markdown 带当前身份认证；缓存按身份隔离，退出后不能通过界面回到私有缓存内容。
- 对选择、加载、错误、禁用、空态写清楚文案；附件失败不把整条记录伪装成成功。

中文换行、长 URL、键盘和大字号在设备验证；自用首版以 iPhone 竖屏为主，不扩展为 iPad 专属布局项目。
系统提供基本无障碍语义，不能只用颜色区别待办状态。

## 5. 页面行为

记录页首屏展示服务数据；全部/想法/待办筛选和正文搜索使用服务合同，记录编辑不改变创建时间顺序。
待办页默认 open，提供 done 与 archived 筛选。空态只有真实操作入口，不展示会被误认成个人数据的样例记录。

详情显示完整正文、创建时间、状态和附件。open 待办提供“完成”“不再做”；终态没有撤销/复活按钮。
“再建一个待办”只预填正文，不复制附件或关联旧 ID；保存仍产生新记录。
笔记与待办创建后不能互转；标题、标签、优先级、项目、提醒均不进入 M1 表单。

AI 页明确后续开放，不连接模型，不提供可发送的假输入框或演示答复。
原型里尚未实现的“聊聊这条”不作为可点击的实际功能交付。
