## 1. 技术与文件归属

使用 Node/TypeScript、Express、Zod，版本与仓库兼容；数据库采用 PostgreSQL 18 的受支持稳定小版本，
开发与部署固定同一大版本。`pg` 执行参数化 SQL，`node-pg-migrate` 管理迁移，不新增 ORM、Redis 或事件队列。
新依赖锁定稳定发布版并提交 lockfile；迁移工具官网当前展示 alpha 文档，不能据此直接安装预发布依赖。

## 2. 身份与连接

唯一所有者有稳定 UUID；部署初始化一次，修改用户名、密码或重新登录不改变 owner。
数据库保存服务实例 `serverId` 与 owner；恢复备份保留二者。换库、换环境或切端点不能自动继承另一环境的身份。

- 用户名/密码登录。密码使用带独立 salt 的密码哈希，不复制现有节点认证中的明文持久化。
- access/refresh token 对客户端不透明；可以采用高熵随机 token，服务端仅保存哈希和过期/撤销信息。
- access 默认有效期 24 小时，refresh 默认 30 天，可由服务配置缩短以验证过期；刷新轮换 refresh token。
- 一次登录对应独立 session。logout 撤销当前 session，管理员重设密码撤销所有 session。
- owner 从认证上下文取得，业务输入严格拒绝 `ownerId`、`createdVia` 等由调用者伪造的字段。
- 所有记录、上传、附件下载和 info 都需认证；仅健康检查无认证且不输出敏感配置。
- M1 原生客户端用 Bearer 和独立 Keychain；不做共享 Cookie、跨 App Keychain、SSO 或注册管理。
- 登录具备按可信来源与账号的有界失败限流，默认不信任公网任意传入的转发 IP 头。
- 无凭据、失效 token 为 401；网络/503 不视为账号退出。日志不写 token、密码、正文或文件内容。

认证路由：`POST /api/auth/login`、`POST /api/auth/refresh`、`POST /api/auth/logout`、`GET /api/auth/verify`。
login/refresh 返回 `accessToken, refreshToken, expiresIn, sessionId, ownerId, serverId`；verify 返回 `valid, ownerId, serverId`。
`GET /api/suiji/v1/info` 返回 `protocolVersion: 1`、server/owner 标识、应用版本、schema 版本及生效的输入/附件限额。
不把未来浏览器的 Cookie/CORS 策略提前设成全来源开放；W1 接入时独立确定允许来源与会话承载。

## 3. HTTP 合同

API 使用 camelCase，数据库使用 snake_case；这是对原交接建议字段的明确映射。
ID 为不透明 UUID，时间为 ISO 8601 UTC，UI 按设备时区显示。共享 DTO 的最小记录结构如下：

```ts
type SuijiRecord = {
  id: string;
  kind: "note" | "task";
  body: string;
  taskStatus: "open" | "done" | "archived" | null;
  version: number;
  createdAt: string;
  updatedAt: string;
  createdVia: "app" | "agent";
  attachments: SuijiAttachment[];
};
type SuijiAttachment = {
  id: string;
  kind: "image" | "markdown";
  fileName: string;
  mimeType: string;
  byteSize: number;
  position: number;
};
```

业务根路径为 `/api/suiji/v1`；成功的单记录响应为 `{ record }`。
除登录/刷新外，业务写操作带 `Idempotency-Key`，内容改变必须对应新的操作；仅凭正文相同不去重。
`createdVia` 由可信入口确定且创建后不变：M1 原生与后续 Web 属于 app，M2 的 Agent 入口属于 agent。
附件 DTO 的 position 表示当前记录中的顺序；上传未绑定时返回附件元数据，不包含 position，绑定后由关联顺序产生。

| 路由                            | 输入                                           | 输出与约束                                                          |
| ------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------- |
| `GET /records`                  | kind、taskStatus、q、from、to、cursor、limit   | `{ items, nextCursor }`；q 只查当前正文；时间为创建时间 `[from,to)` |
| `GET /records/:id`              | 记录 ID                                        | 当前完整正文、状态、附件与版本                                      |
| `POST /records`                 | kind、body、可选 attachmentIds                 | 201；note 状态 null，task 状态 open；版本 1                         |
| `PATCH /records/:id`            | expectedVersion、可选 body、可选 attachmentIds | 200；一次保存原子更新正文和附件；禁止修改 kind/status/时间/owner    |
| `POST /records/:id/task-status` | expectedVersion、targetStatus                  | targetStatus 只允许 done/archived；只允许从 open 转出               |
| `POST /uploads`                 | 单个 multipart file                            | 201 `{ attachment }`；获得待关联附件 ID，上传也使用幂等键           |
| `GET /attachments/:id/content`  | 附件 ID                                        | 鉴权后的实际文件流；不返回主机路径，不重定向到公开静态目录          |

PATCH 省略附件表示保留，显式 `[]` 表示清空；省略 body 表示保留。至少提供一个可修改字段。
服务以修改后的整体内容检查非空：允许纯附件，禁止空白正文且附件为空。严格保留原文空格、换行和 URL；
空白判断不回写 trim 结果。Unicode 长度统一按标量计数，拒绝 NUL/不合法 Unicode，并明确返回输入错误。
附件限制和格式见总体计划；iOS 可选择 HEIC，规范化为 JPEG 后上传，服务器只接受实际 JPEG、PNG 或 UTF-8 Markdown。

**与交接建议的差异：** 正文和附件使用同一个白名单 PATCH，以避免用户点一次保存却发生两次提交、出现半成功。
未来 MCP 的 replace-body 只传 body，仍保留其他字段；待办状态保持专用端点。

列表默认 20、最多 100；按 `(created_at DESC, id DESC)` 游标分页，编辑不会置顶。
游标绑定过滤条件，跨条件使用返回 400。正文 q 按字面子串搜索，转义 `%`、`_` 和转义符，中文与 URL 可查；
不接语义搜索、标签、附件全文或外链内容。不同状态的内容可进入全部流，未完成列表仅包含 open。

统一错误体：`{ ok: false, error: { code, message, retryable, details? }, requestId }`。

| HTTP / code                  | 客户端行为                                                  |
| ---------------------------- | ----------------------------------------------------------- |
| 400 / INVALID_ARGUMENT       | 保留编辑，说明不合法字段；不重复原请求                      |
| 401 / UNAUTHENTICATED        | 尝试恢复认证；明确失败才重新登录                            |
| 404 / NOT_FOUND              | 不存在或当前 owner 不可访问；不透露其他内容                 |
| 409 / VERSION_CONFLICT       | 返回有权读取记录的 currentVersion；保留草稿，读取最新版比较 |
| 409 / INVALID_TRANSITION     | 不重试复活旧待办                                            |
| 409 / IDEMPOTENCY_KEY_REUSED | 同 key 的 operation/请求内容不同；拒绝新副作用              |
| 413 / PAYLOAD_TOO_LARGE      | 指明限额，不截断后保存                                      |
| 429 / RATE_LIMITED           | 提供 Retry-After；写操作等用户重试                          |
| 503 / DEPENDENCY_UNAVAILABLE | 不能表示已保存；结果不确定的重试沿用相同 key                |

## 4. 数据、事务与附件生命周期

除身份和迁移元数据外，M1 业务表只包含：records、attachments、record_attachments、record_revisions、mutation_requests。
attachments 表示不可变上传对象；record_attachments 表示当前有序关联，使未关联上传与历史快照的引用都可表达。
附件保留所属 owner 与首次绑定的 record，拒绝被另一个 record 重用；创建相同待办只复制正文。
records 与快照/关联使用 owner+record 的一致归属约束，note/task 状态约束同时在数据库和业务服务验证。
M1 不开放删除，也不添加只为未来使用的删除状态、向量表、索引 worker 或关系字段。

一个写请求的边界：

1. 完成认证、严格输入校验；hash 包含 operation、目标 ID、expectedVersion 和完整规范请求。
2. 同一数据库事务内申请唯一 `(owner_id, idempotency_key)`；同 key 相同请求返回保存的结果，不同请求返回 409。
3. 获取记录行锁并检查 expectedVersion、状态与附件所有权；更新记录、当前附件关联，版本递增。
4. 创建版本 1 或新版本的完整快照，保存最小幂等成功结果；一起提交后才向客户端返回。
5. 任一步失败整体回滚；不能先提交 processing 占位，也不能把文件上传或模型调用放入业务事务。

并发同 key 的唯一约束等待、事务快照重读和锁超时必须在真实 PostgreSQL 验证。
同版本的不同写请求只能一个成功；原样重复、无字段变化的编辑不新增版本，但记录其幂等结果。
失败不留下已完成幂等结果；同 key 的成功重放不得再次改变 updatedAt、版本或附件关系。
事务中所有语句使用同一个 `pg` client。[node-postgres 事务约束](https://node-postgres.com/features/transactions)

附件采用服务端生成的随机 object key，文件名仅作显示。路径拼接不能接受客户端目录或逃逸根目录。
流式限制字节数、校验真实类型与 Markdown UTF-8，临时写完后原子转为不可变文件，再登记元数据；
失败可以留下待排查的孤立文件，不能留下可被成功关联却缺文件的附件。重复上传相同 key 不生成第二个逻辑附件。
上传请求摘要使用文件内容摘要、规范文件名与类型等业务字段，不包含随机的 multipart boundary。
新建/编辑只关联已就绪且归属正确的附件；对象内容不就地覆盖，移除关联不删除被历史版本引用的文件。
没有垃圾清理任务；磁盘容量与孤立文件数量必须可观察，后续清理另定保留规则。
下载验证 owner，使用正确 Content-Type 与 nosniff；Markdown 作为文本，不运行其中的 HTML/JS、不拉取内嵌远程图片。

## 6. 需要实现的命令合同

```bash
pnpm --filter @runweave/suiji-server typecheck
pnpm --filter @runweave/suiji-server lint
pnpm --filter @runweave/suiji-server build
pnpm --filter @runweave/shared typecheck
pnpm architecture:check
pnpm --filter @runweave/suiji-server db:migrate
pnpm --filter @runweave/suiji-server auth:init
pnpm --filter @runweave/suiji-server start
node deploy/suiji/release.mjs deploy --config <绝对配置文件> --image <不可变镜像引用>
node deploy/suiji/release.mjs backup --config <绝对配置文件>
node deploy/suiji/release.mjs restore --config <隔离目标配置文件> --backup <备份目录>
```

typecheck/lint/build 零退出仅证明静态与产物门禁；真实功能按 YAML 独立判定。migrate 重复执行无新增副作用；
auth:init 只从受保护环境/stdin 取得密码，绝不通过命令行参数输出或传递秘密。
运行时配置 `DATABASE_URL`、迁移身份 `MIGRATION_DATABASE_URL` 与 `SUIJI_STORAGE_DIR` 从配置载入，不回显连接串。

release 配置必须包含 environment、目标主机/路径、域名/TLS 接入、备份位置、声明的 RPO/RTO 与允许短暂停写窗口。
缺项时预检列出字段名并停止，不能推测生产地址。首次发布前才需要用户提供这些实际环境事实；本地 M1 使用隔离 dev 配置可继续。
部署锁覆盖预检、有效备份、迁移、换版和就绪检查。失败保留旧产物与日志；禁止自动删除卷、清库或 reset 生产数据。
数据库版本参考 [PostgreSQL 支持列表](https://www.postgresql.org/support/versioning/)；
迁移锁与默认事务行为参考 [node-pg-migrate 官方说明](https://salsita.github.io/node-pg-migrate/migrations/)。

## 7. 风险与明确非目标

最重要风险是超时重复写、并发覆盖、正文与附件半成功、身份变化导致记录不可见、备份只有 DB 没有文件。
以上必须取得真实服务证据，不以 schema 或 UI 显示成功代替。
没有多用户产品、任意 SQL/SSH 工具、AI 调用、后台清理、远程链接抓取、iCloud 或数据库大版本自动升级。
服务端单人模式仍在 SQL 中固定 owner 过滤；验收使用越权/未知 ID 和独立测试部署，不能伪造已支持多用户注册。
