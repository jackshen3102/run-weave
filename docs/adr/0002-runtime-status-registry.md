# ADR-0002：使用统一注册机制提供运行状态

- 状态：已接受
- 日期：2026-09-06

## 背景

Runweave 中需要观察的运行依赖持续增加，已经覆盖进程、单实例认领、端口、WebSocket、内部事件流和周期任务。若每增加一个依赖就为面板编写一套专用数据与 UI，状态语义、重试规则和异常提醒会再次分散。

运行状态面板需要保持简单，但底层必须允许不同运行时用一致方式增加状态项，避免它退化为只覆盖当前问题的一次性页面。

## 决定

Runweave 使用统一的运行状态注册机制提供状态项。

- 跨运行时共享状态项的身份、状态、来源和时间语义。
- 每个运行时通过自己的注册表或等价提供者暴露所拥有的状态项。
- 状态拥有者负责健康判断和重试策略，注册机制不主动探测所有组件。
- 每个状态项声明稳定的能力域归属；客户端先按能力域聚合，再展开显示真实状态项。
- 能力域状态取所含状态项中最严重的状态，应用级入口统计异常能力域数量，避免连锁故障放大异常计数。
- 状态项可以声明必要的上游依赖；上游异常时，下游表达为“无法判断”，不重复计数或提醒。
- 客户端按统一报告结构合并与渲染，功能专用 UI 只用于确实特有的详情或导航。
- 新增长期进程、端点、连接或周期任务时，可以接入同一机制，但是否纳入面板仍由产品范围决定。
- 注册机制不是用户插件系统，不引入独立 daemon，也不承担指标、追踪或长期告警存储。

## 备选方案

### 为当前状态项写死面板

不采用。初始成本较低，但每次新增依赖都要同时修改采集、聚合、提醒和 UI，容易再次产生互相矛盾的状态定义。

### 由中央组件主动探测所有运行时

不采用。中央组件不了解各依赖的真实生命周期和重试边界，并会引入反向依赖与假健康。

### 接入通用监控或遥测平台

当前不采用。它超出了本机操作型状态入口的需求，并增加部署、存储和隐私边界。

## 后果

- 新状态项可以复用身份、合并、提醒和通用展示能力。
- 状态合同需要保持稳定并处理不同运行时版本之间的兼容。
- 每个运行时仍需为自己的状态项提供可靠判断，注册机制不会自动获得健康语义。
- 通用 UI 需要允许状态项携带少量可复制信息和导航目标，但不能演化为任意远程控制协议。
- 注册粒度与展示粒度不同：运行时按可独立失败的边界注册，界面按用户可理解的能力域组织。
- 第一版只接入会直接造成用户功能失效的关键故障域；低风险内部循环后续按需注册，不阻塞机制和界面落地。
- 聚合需要保留最小依赖关系，避免一个上游故障被展示成多个彼此独立的异常。
