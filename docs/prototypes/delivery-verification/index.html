01

先补工作方法，复用已有能力

现有 Runweave 已经能创建独立任务、读回原生结果、登记审查，并按完成条件核对报告。这次建议增加一个薄的 delivery-verification 技能，明确何时核验、核验什么、如何收口。

已有

独立执行与返回

通用终端任务绑定独立身份，保留派发记录、原生结果与审查记录。无需再建一套多角色调度。

拟新增

围绕目标组织验证

从用户原始要求提取必要条件，把当前版本、实际操作、结果和独立判断逐项对应起来。

保留边界

Runtime 记录执行事实

报告保存、任务结束、反馈清零都不能自动证明业务达标。监督器继续只做报告核对。

角色名称成本很低，判断依据才是重点。

默认一次独立目标核验。需要不同专业能力时再拆分，不预设 Developer、Skeptic、User 四角色流水线。

触发范围：显式调用本技能，或明确要求独立核验最终交付是否达到原始目标。普通开发、写计划和纯提交 PR 不自动触发。

02

从用户要求到最终交付

每一步围绕同一份完成条件展开。已有授权继续有效，不在阶段切换时反复请求确认。

01

确定条件

原始要求 → 用户可观察结果 → 必要验证。保留后续范围修订。

02

执行与取证

记录版本、入口、操作、预期和实际结果。复用已有工具。

03

独立核验

新上下文读原始条件与证据，必要时复跑关键路径。

04

回归与返工

按改动影响选择回归。修复后更新受影响证据。

05

逐项交付

列明已验证、失败、未验证及用户取消；真人确认另记。

验证做到什么程度？

  • 必要：去掉它会漏掉重要失败。
  • 充分：承诺的每项结果都有适用证据，没有未处理反证。
  • 合理：用最低成本覆盖不变量，不重复造证明。

有限验证不能证明所有场景都正确。

哪些证据需要重跑？

相关代码、配置或构建改变，重验受影响项。未受影响的证据可以复用，并说明为什么仍适用。

只记录 HEAD 不够；未提交修改需对应 diff / 内容摘要，安装态需对应实际构建。

反馈用于追踪已发现的问题。影响必要条件的问题必须处理，但“零反馈”或“全部关闭”不是 Runtime 完成门禁。
03

独立目标核验，保留代码 Review 的隔离

两种判断看不同资料，解决不同问题。代码审查无发现，不能替代原始目标核验。

手机上可在下表内部横向滑动。

判断看什么解决什么返回含义
现有代码 Review
保持原边界		冻结代码快照、白名单资料；不读来源会话和目标。实际复现代码风险，检查对应范围。报告无发现只适用于该审查范围。
拟议目标核验
复用通用任务		必要用户原文、已采纳条件、版本、入口和证据。检查交付是否达成原始目标，是否遗漏或扩张。逐条件说明实际结果与依据，主 Agent 核对后收口。

交给核验者

  • 原始要求及用户范围修订。
  • 完成条件、采纳规格和来源位置。
  • 精确版本、真实入口、证据路径。
  • 只核验不修复的职责与操作范围。

避免带入判断偏向

不传完整探索对话，不把“我们已经做完了”作为前提。实现者报告只是待核对资料。

独立上下文不等于文件系统沙箱：核验者只使用自有验证资源，不修改实现或用户数据。

结果怎样可靠交回来？

复用 create → start → send → observe/wait → review。保留同一 Backend、taskId 和固定身份；每轮使用新的 dispatchId，revision 来自最新观察。

  • written / received 只表示输入写入或被看到。
  • 取得原生终态和完整 final 后，才核对报告。
  • delivery_unknown 先观察，不换 ID 重发；人工接管不自动夺回。
  • task review accepted 表示核验报告合格。报告指出产品失败时，产品仍然没有通过。

什么情况下可以说“完成”？

当前证据

桌面操作和窄屏模拟已通过，指定 iPhone 尚未验证。

尚未完成必要验证

手机阅读仍是必要条件。设备可用就继续实测；设备不可达且无独立步骤时，报告验收阻塞。手机圈选不进入本期义务。

技术验收与真人确认分开记录。只在用户要求、约定流程或主观判断需要时等待真人确认；Agent 扮演 User 不构成用户签字。

8 个验收关注点

01 · 写计划不会自动扩成实现

02 · 独立上下文真实建立并返回

03 · 任务结束不掩盖业务失败

04 · 旧证据按影响范围更新

05 · 桌面不能代替手机真机

06 · 真人确认不被代签或滥加

07 · 未知投递不导致重复交办

08 · 用户范围修订优先于旧计划

本轮明确不扩展的范围

不新增反馈系统、角色注册、DAG 调度、完成按钮或原生客户端协议。不改变现有 Runtime 的报告核对语义，不改变代码 Review 来源隔离，也不自动启用所有任务的强制验收。

手机阅读是方案载体要求；手机圈选继续延后。

风险与回滚

主要风险是复述实现者结论、误用旧证据、扩大授权和核验成本过高。通过原始输入、版本适用性、明确触发范围和默认一次核验控制。

不迁移业务数据。撤回新增技能并沿用 Toolkit 同步机制即可回滚；已有任务及证据保留。若收益不足，缩减步骤。

结论从哪里来

方案基于本地源码阅读。以下路径可在同一项目核对；不把静态阅读视为运行验收。

  • backend/src/task-supervision/assessment.ts：逐项状态、来源校验及 hold；明确不执行独立验收。
  • backend/src/task-supervision/deliverables.ts：有界读取显式引用，快照不等于运行结果。
  • backend/src/terminal/tasks/service.ts 与 docs/cli/terminal-task-control.md：任务身份、原生返回、派发及 review 语义。
  • backend/src/terminal/code-review/prompt.ts / report.ts：冻结输入、来源隔离及同版证据约束。
  • plugins/toolkit/skills/acceptance/SKILL.md：真实材料、手机入口与真人验收边界。
