# 执行优化原型：耗时与 Token

两个独立方向：执行耗时、Token 用量。每个方向分别展示候选、测量和处理结果，没有综合分数。
只调整原型与样例，不修改正式产品，不启动定时任务或模型。

## 启动

```bash
python3 -m http.server 6188 --bind 127.0.0.1 --directory docs/prototypes/token-review
```

打开 `http://127.0.0.1:6188/`。默认直接读取历史日志测量样例，无文件导入导出、无独立定时设置。

## 当前展示的两条记录

此前九条通用流程疑点已移出本版本；流程描述、报错和重复次数不足以单独成为效率记录。

### 执行耗时

- 完整构建到 `shellReady: true` 为 **53.544 秒**，原任务目标为 30 秒。
- 日志 `rollout-2026-09-26T10-40-21-01a0db95-c8af-7c30-a9ba-4300045a033b.jsonl`：L1695 包含命令内部计时与 shellReady；L1748 为同源码复用 10.379 秒；L1915 记录目标与历史结论。
- 直接读取的是工具内部计时，不使用外层工具调用的 Wall time 冒充构建全程。
- 首次完整构建与同源码复用属于不同条件，不做差值节省率。当前仅一个完整构建样本，无 p95、稳定耗时或当前版本回归结论。
- 这是历史优化候选，是否仍需处理须用户结合当前版本复核。

### Token 用量

- 日志 `rollout-2026-09-26T10-50-04-01a0db9e-ae44-7c93-a75a-56b79863fa07.jsonl` 中 12 次 `wait_agent({timeout_ms:10000})`，其中 9 次超时。
- 每次取调用前最近的累计用量与对应返回后首条累计用量，12 个不重叠区间分别相减再求和。
- 输入 **689,270**，其中缓存 **672,896**，未缓存输入 **16,374**，输出 **906**。模型为日志 turn_context L8 的 `gpt-6-sol`。
- `mock-state.json` 保存每段 before/after 原始计数、来源行号及调用返回位置；页面直接根据这些计数求差值，展开可核对全部 12 段。
- 这是与调用相关的模型用量区间，包含准备调用的推理；不是工具自身消耗，也不是可全部消除的浪费。计费方式与服务档位未确认，不提供金额估计。
- 入列是人工选择的“大量上下文与短等待重复关联”候选，需考虑 97.6% 缓存比例后复核收益；不是自动判定 12 次等待不合理。优化效果尚无同条件样本。

## 可以实现的能力与实际缺口

| 原型能力 | 现有依据                                                                                               | 正式接入仍需完成                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 用量证据 | `scripts/token-report/logs.mjs` 已解析累计输入、缓存、输出并去重                                       | 保留采样点、模型信息、工具 call_id 和区间边界；前后计数回退或缺失时不生成精确观测值 |
| 耗时证据 | 真实工具结果含内部 elapsed；日志含调用/返回时间及轮次时间                                              | 内部计时优先；时间戳差须标为区间耗时，不能自动排除人类等待，也不把并行阶段相加      |
| 周期执行 | 现有 `backend/src/scheduled-tasks/providers/codex.ts` 启动 Codex，并传入提示语；任务拥有模型和周期配置 | 用任务提示语或 Skill 调用统计分析，补上持久化检查点、结构化记录写入和稳定记录 ID    |
| 单条处理 | 当前原型已实现状态、文字记录、显式完成确认与本机保存                                                   | 正式 API/数据库持久化、来源任务及运行关联；用户状态不能被每日分析覆盖               |
| 补充分析 | 页面可记录需要核实的问题                                                                               | 实际 Agent 执行入口和结果回收仍需接入；当前不会生成虚构分析结果                     |
| 效果验证 | 可提交同条件测量的结果和证据，由用户确认                                                               | 自动同任务基线匹配、节省估算、自动复发判定不在首版范围                              |

统计程序不调用模型；定时任务本身启动 Codex 仍可能产生消耗。分析自己的用量需单独回收，不能承诺空跑零 Token。
初版先按程序统计和有限证据分析筛选，具体入列阈值需结合真实分布校准；无量化影响、影响轻微或只有一般流程建议的结果不入列。
不自动将大任务判为低效，不按 Skill 独占归因，不跨两个方向合并分数或收益。

## 交互与边界

- 两个方向有各自的待处理、处理中、已处理、暂不处理、已排除；记录身份包含方向，处理一侧不会改变另一侧。
- 列表显示观测耗时或观测输入，原因分类只是辅助筛选。详情包含统计区间、原始证据、不确定性和验证方向。
- “观测值排序”只在当前方向内比较，不代表浪费排名或优化收益排名。
- 确认完成需填写措施、同条件验证结果及证据，并显式勾选确认；没有自动关闭记录。
- 当前没有关联真实分析任务，页面显示暂无运行，不伪造定时任务结果、覆盖统计或分析消耗。
- 状态保存在本浏览器 `localStorage` 的 `token-review-prototype-v3`；旧版状态未删除，也不套用到新方向。无服务端同步。
- 主列表只接收明确方向、量化测量、入列依据与证据齐备的候选；正常执行和通用经验不补位。合并只接受明确的同方向问题身份。当前测量是所选区间，不自动汇总全部关联任务的用量。
