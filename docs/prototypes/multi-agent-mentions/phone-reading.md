# 方案 04：先改 Review Agent

入口就在原生 CLI。输入 `@review 检查当前改动` 后，当前 Agent 用 Skill 代发，独立 Reviewer
负责审查，结果回到当前 CLI。不新增产品页面，不依赖 Runweave 图形输入框。

```text
你：原生 CLI 输入 @review
          ↓
当前 Agent：读取 review-agent Skill
          ↓  rw terminal review start
现有 Backend：冻结代码和用户要求
          ↓
独立 Reviewer：自己的会话 + review-only 职责
          ↓  保存报告
当前 Agent：show / wait 读取真实报告 → 原 CLI 汇报
```

本次新增 start/list/show/wait 命令和代发 Skill，复用现有审查服务、独立会话、请求去重、
事项轮次及结果回传。Skill 不再发一遍自动反馈，Reviewer 不递归派工。

**独立会话与复审。** Reviewer 不默认获得实现者完整对话，只读取冻结改动、用户要求及
明确引用。用户要求新一轮复审后冻结新快照；原 Reviewer 空闲且未被人工接管时复用，
否则由服务创建新会话。当前入口不是任意聊天转发。

**结果。** “已开始”“审查结束”“覆盖完整”“目标已验证”和“反馈写入”分别判断。
等待超时只返回当前状态，不取消任务或重新派发；同一请求保留同一编号。无发现不能代替目标达成，
过期快照、缺失验证及失败均明确报告。不会自动关闭事项。

**必要前提。** Runweave 托管的 CLI 自带来源终端身份；外部 CLI 必须明确指定来源终端和连接。
审查来源项目当前未提交改动，不是任意 shell 的 cwd、PR 或文件过滤。需要新版 CLI/Skill 和既有 Backend Review 服务。
@ 是提交后由 Agent 理解的文本，不承诺原生补全菜单；自动选择 Skill 仍有模型依赖。

**下一步才通用化。** 保留同时 @多个 Agent、分别工作、独立上下文和定向追问的目标。
后续补别名注册、每目标投递与回执、忙时策略。Review 作为具有冻结审查合同的专门适配器接入，
不把所有 Agent 都变成 Reviewer。跨机器、跨执行器、重启恢复与异步通知尚未完成。

**已有证据。** 之前在原生 Codex 做过临时 Skill 多目标代发：两位分别返回 1156/2298，
单目标追问返回 1158；未知目标未投递、重复请求未重复执行，共 8 项通过。那是可行性探针，
不是正式 Review 功能验收；没有 Pi/Claude 发起端证据。社区资料参考独立会话、多目标及定向沟通，
没有安装运行社区产品。

手机可直接读这份会话内文字；原 HTML 手机打不开的原因尚未确认，不宣称真机已修复。

**本次已实测。** 本次构建的 CLI + 原生 Codex + 临时项目中，当前 Agent 读取新 Skill，启动不同 thread 的独立 Reviewer，最后用 show 读回报告。9 项链路与隔离核对通过；样例 8 组调用通过。全局实例参数拒绝问题在实测中发现并修复，沿原请求编号恢复成功。重复请求、等待到期和输入拒绝也已核对。临时环境已清理，未全局安装或发布。未重测有发现时反馈、复审复用、其他 CLI 发起端、重启与压力。

**后续修复复验。** 已修正查询超时和跨检查证据关联。原拒收报告可在隔离存储归档，非法证据仍拒收；15 个 CLI 传输场景通过。源码 Backend 中，原生 Codex 通过 Skill 派出 Reviewer，真实发现临时样例错误，报告入库、自动回传、发起 CLI 读取及确认反馈均已验证。验证环境已清理，尚未更新全局安装。
