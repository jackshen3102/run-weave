快捷指令的两种后台方式：纯后台调用 + 临时终端「完结即焚、受阻保留」

在保留现有「纯后台静默运行」的基础上，为需要真实终端环境的快捷指令新增「临时终端」模式：像全权限定时任务一样在当前项目/Worktree 新开专用 tmux 终端执行，顺利完成后自动关掉终端；一旦遇到受阻或人工接管则原样保留终端不关闭，方便直接切入现场处理。

一、两种后台执行方式的分工（现状 vs 拟新增）

经核对源码，当前快捷指令一律走非交互子进程；而普通定时任务虽已有专用终端适配器，但显式排除了快捷指令，且受阻时仍会删除终端。

1. 纯后台方式（headless）

当前已有 · 默认

由 CodexScheduledTaskProvider 直接启动非交互 codex exec --json --output-schema 进程，后台读取结构化事件流。

  • 不创建 PTY 或 tmux 会话，主动剥离 RUNWEAVE_TERMINAL_SESSION_ID 与 TMUX_PANE。
  • 优势：零终端列表噪音、完全静默，适合研究总结、文档整理、纯静态检查等任务。
  • 边界：遇到依赖当前终端身份、绑定终端右侧 Browser 通道或需要 TUI 原生交互的指令无法执行。

2. 临时终端方式（terminal）

本次拟新增 · 已选旁路裁判

在发起快捷指令的原项目 / Worktree 下新建专用 tmux 终端启动原生 Codex TUI，原样发送快捷指令（不拼接裸 JSON 协议，保留自然语言与 /slash 兼容）。

  • 具备完整终端身份：拥有真实 terminalSessionId、panelId 与交互式 Shell/TUI 环境。
  • 旁路独立裁判完结即关：到达 agent_idle 后复用 TaskSupervisionClassifier 只读分类，仅高置信确认 completed 时自动回收终端。
  • 「宁留勿删」保留现场：硬信号阻塞、判定 blocked、置信不足（hold）、报错或人工按键介入时一律不关终端，写入 terminalBinding(ready) 直达人话现场。

二、怎么判断「执行完成 vs 受阻」？（已选定路线 B：硬信号 + 旁路独立裁判 + 宁留勿删）

交互式 TUI 无法挂载底层 --output-schema，且强迫执行 Agent 吐裸 JSON 会破坏 /slash 命令与现场可读性。方案采用两层判定 +「宁留勿删」保守关窗原则：

① 免打扰参数拉起新终端

沿用定时任务参数（禁启动升级检查、免审批、跳过 Hook 信任确认）拉起 Codex TUI，原样提交指令。

② 层 1：轮次中硬信号监测

实时监测提问 Hook、权限请求、OSC 7501 blocked 与终端人工按键（takenOver）。

③ 层 2：空闲后旁路结构化裁判

进入 agent_idle 后调用只读 TaskSupervisionClassifier（--output-schema + 分差门禁）核对完成条件。

④ 宁留勿删处置

仅高置信 completed 自动关终端；continue 原终端续跑；blocked / hold / 报错 一律保留现场。

判定分支 信号来源与触发条件 临时终端处置 看板与终端绑定状态
高置信完成 (completed) agent_idle + 旁路分类器 disposition="apply" 且全部完成条件 reported_done/waived（得分 ≥ 0.70、分差 ≥ 0.20） 自动关闭终端 completed，保留自然语言最终回复摘要；事后仍可按原 threadId 恢复新终端
仍有获准剩余步骤 (continue) agent_idle + 旁路分类器判定原授权内尚有明确下一步（未超 3 次且有进展） 同一终端内续跑 running；直接在当前临时终端追发具体下一步，无需销毁重建，全部完成后再自动关闭
业务受阻 / 反问用户 (blocked) agent_idle + 旁路分类器判定缺用户输入、缺登录/权限、遇冲突反问，或续接满 3 次仍未完成 保留不关闭 看板置顶「需处理 · 终端已保留」，写入 terminalBinding(ready)；切过去看到的是干净的人话现场
置信不足 / 报错兜底 (hold / error) 旁路分类器覆盖不全、分差接近（hold），或 CLI 异常退出 / 分类超时 保守保留不关闭 宁留勿删：只要不确定已全部完成，最坏仅多留一个终端供你扫一眼关闭，绝不误删现场
轮次内硬信号挂起 未到空闲，卡在 request_user_input / PermissionRequest / OSC 7501 state=blocked 保持打开等待 复用既有待确认通知；进终端按键即转已接管保留；若通过手机回复辅助答完并最终 completed 仍自动关窗
用户中途接管 / 主动停止 运行中用户在终端按键（takenOver）；或主动点「停止运行」 人工接管 → 保留
主动停止 → 关闭		 人工接管立即解除自动关窗；主动停止在确认中断进程树后回收终端（未确认则保留并标 stopping）

四、关键决策状态（判定路线已拍板，余 2 项轻量交互确认）

核心难点「完成 vs 受阻判定」已确认为路线 B；其余两项交互细节默认采用推荐项即可直接进入实现：

已确认决策：怎么判断「执行完成 vs 受阻」？

已拍板：路线 B（旁路独立裁判 + 宁留勿删）

不向原终端拼接裸 JSON 输出协议，保持 TUI 对话与 /slash 指令纯净可读；结合轮次内硬信号（Hook / OSC 7501 / 人工按键）与轮次空闲后的只读 TaskSupervisionClassifier（--output-schema + assessClassification 置信门禁）：只有高置信确认 completed（或主动停止）才自动关闭临时终端；blocked、hold（不确定）及运行报错一律保留终端现场。

待确认 1：后台方式配置在哪里？

默认推荐：按每条快捷指令保存

同一台电脑上，「研究一次」适合纯后台，而「浏览器验收 / 更新桌面端 / 提交 PR」需要终端，是否依赖终端由指令内容本身决定。

待确认 2：新开临时终端时，是否抢占当前正在看的终端焦点？

默认推荐：静默新建，受阻再切

普通定时任务当前使用 activate: true 自动切入新终端；但快捷指令通常是在你正盯着某个终端干活时顺手点开的。

六、可验证结果与验收计划

  • 纯后台回归不退化：headless 快捷指令点击后不产生新 TerminalSession，原终端草稿与焦点不变（对应 BGC-001）。
  • 临时终端完结自动回收：terminal 快捷指令启动后在目标 Worktree 下创建专用 tmux 会话；返回 succeeded 后会话从 TerminalSessionManager 与 tmux ls 中确认消失，摘要与输出保留在运行记录。
  • 受阻原样保留且单实例接管：返回不可自动续接的 blocked（或中途在终端输入接管）后，原 tmux 会话与 Codex TUI 保持存活，run.terminalBinding.attachmentState === "ready"；点开直接进入同一 terminalSessionId，不新建第二个终端，后台 continue 明确拒绝并发双跑。
  • 静态与真实验收门禁：实施阶段依次执行 shared/backend/frontend typecheck & lint、pnpm architecture:check、pnpm docs:check、pnpm scheduled-tasks:verify-runtime，并在隔离 Dev Session 补充扩展 docs/testing/background-commands/core.testplan.yaml 用例取证。
