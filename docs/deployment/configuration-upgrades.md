# 配置版本与升级迁移合同

本文固化已确认的维护约定：**迁移层负责旧格式，业务代码只消费当前目标版本的配置。**
适用于 CLI、Backend、App Server 及其他受管配置消费者；纯服务端通过 npm 交付，
本地 Mac 桌面端保留源码更新方式，两种交付方式遵循相同的配置合同。

## 实施状态与操作边界

这是实现和发行必须遵循的合同。下表描述当前源码；目标机器是否具备这些能力，须核对实际安装版本与 CLI 帮助，不能由文档推定已发布。

| 能力                                                              | 当前状态                                                                                                   |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 独立实例 YAML、字段定义、校验、私有备份、revision/digest 冲突检查 | 已有，见[配置 CLI](../cli/configuration.md)                                                                |
| 旧 JSON / 环境文件导入 YAML                                       | 已有 `rw config migrate --source-manifest`，不是发行版本之间的迁移链                                       |
| 配置已保存与进程已生效的区分                                      | 已有，见[服务管理](../cli/service-management.md)                                                           |
| 随发行包交付的逐版本迁移链、预检及更新事务集成                    | 已接入 `rw config upgrade` 和 `rw server update --dry-run`；当前结构版本仍为 1，尚无需要转换的正式迁移步骤 |
| 通用迁移引擎与故障恢复验收                                        | 安装验收脚本已接入隔离 CLI 合成版本迁移；每个正式字段迁移仍需对应旧配置 fixture，不由通用验收替代          |

当前 Server 发行包通过 `configurationUpgradeVersion: 1` 声明迁移协议，数据库指纹
`databaseCompatibility` 与配置迁移分开判断。入口为 [build-server.mjs](../../scripts/release/build-server.mjs)
和 [update.ts](../../packages/runweave-cli/src/server/update.ts)。数据库指纹仍须一致，不自动迁移数据库。
旧发行包只有组合指纹时，构建脚本使用已记录的历史配置源码摘要与**当前数据库源码**计算
`legacyDataCompatibility`；只有旧组合指纹匹配才能升级，不按 npm 版本号猜测数据兼容性。
历史摘要来源在 [legacy-configuration-fingerprints.json](../../scripts/release/legacy-configuration-fingerprints.json)。

候选包内的 `config-plan` / `config-apply` 是内部协议，由管理 CLI 调用；迁移代码来自候选包，
不会从配置文件加载脚本。旧包缺少协议时仍保留组合指纹检查，不强行进入新迁移流程。
Agent 发现目标需要迁移却没有受支持的执行入口时，在切换前停止，报告缺失能力。
不得臆造参数、手改版本号骗过校验，或现场生成脚本改生产配置。

## 版本和所有权

- npm 程序版本、配置结构版本、配置编辑次数分别管理。`schemaVersion` 表示文件封套版本，
  `domainVersions` 表示各配置域版本，`revision` 表示写入修订次数，不能互相替代。
- “最新配置”指本次目标程序要求的结构，不是 registry 中最新包要求的结构。
  每个发行版声明它管理的配置域、目标版本及可迁移的源版本；只有结构或语义变化才增加对应版本。
- 活跃配置只保留迁移后的目标结构，不并存新旧字段，不在业务模块长期保留旧字段 fallback。
  历史结构只存在于私有备份和迁移模块中；保留迁移链以支持跨多个发行版升级。
- YAML 位于实例自己的持久目录，npm 包包含定义、默认值和迁移代码，不包含实例配置或密钥。
  CI 使用隔离的合成配置，不能收集生产凭据作为 fixture。
- 一份配置的所有读取者属于兼容性检查范围。CLI 先更新也不能自行迁移仍由旧 Backend
  读取的共享域。迁移计划要核对 CLI、Backend、App Server 及实际读取同一文件的其他进程；
  暂存候选程序，按共同支持的目标切换，无法协调时在停服前阻止升级。
- 不同实例、不同服务独立持有配置。飞书 Hub 保存应用凭据和 Backend 注册信息，
  Node 保存 Hub 地址与自身 token；新增节点是接入操作。独立 Hub 保持独立维护，
  不纳入 Server 自动部署，也不因主服务升级而顺带迁移或重启。

## 配置变化如何随版本交付

| 变化                     | 发行要求                                                                           |
| ------------------------ | ---------------------------------------------------------------------------------- |
| 新增可选字段             | 默认值兼容旧行为；无需写盘的新增不制造空迁移                                       |
| 新增集成或功能           | 默认关闭或保持原行为，只在启用时要求其凭据                                         |
| 字段改名、类型或结构变化 | 增加对应版本，交付确定的转换步骤，成功后删除旧字段                                 |
| 默认值或隐式语义变化     | 作为行为迁移处理；必要时把旧实例原本生效的默认值写成显式值，避免升级后悄悄变更行为 |
| 删除字段                 | 迁移明确转换或移除并报告影响；不能静默丢弃未识别字段或其他服务拥有的配置域         |
| 缺少必须的新信息         | 预检说明缺失项；不能推导的密钥、地址或用户选择不得猜测，补齐前不切换               |

迁移步骤具有稳定标识、源/目标版本和前置条件，例如域版本 `1 → 2 → 3`。
已发布的步骤不改写历史语义；修正已迁移的结果使用后续步骤。
迁移只转换配置副本，不联网申请凭据、不修改数据库、不发送消息或启动业务任务。
已到目标版本时为空操作；重复执行、进程崩溃后的恢复不能重复产生副作用。
遇到未来版本、缺失迁移链或未知结构，保留原件并拒绝写入，不降级解析。

新增可选字段可以继续使用读取时默认值；“最新结构”不要求把所有默认值写满 YAML。
默认值兼容规则与实际字段定义必须在同一次发行中核对。

## 目标机器的升级事务

受管 Server 更新按以下流程执行；独立配置升级只执行预演和离线配置提交，不切换程序或启动服务。

1. **定位并暂存**：固定 CLI/Server 精确版本、实例、服务用户、配置路径和所有消费者，
   下载候选发行包并校验来源、完整性和运行环境。此阶段不改活跃配置。
2. **预演**：读取源配置的版本、revision 和 digest，在私有副本上计算完整迁移链，
   用候选版本规则校验结果。输出脱敏的字段变更、缺失项、需重启的消费者、数据库兼容结论
   及恢复条件。没有变化时不重写文件。预演不能因旧配置不符合新 schema 而在迁移前误拒绝。
3. **建立恢复点**：保留旧程序、原始配置、启动方式和恢复记录；数据库需要备份时使用一致性方法。
   所有必需信息和预检通过之后，才进入任务排空、维护租约及服务切换阶段。
4. **受控提交**：停止受管 Backend / App Server，检查实例已登记消费者的 owner 锁，以迁移锁阻止新版消费者同时启动。
   独立或未登记的消费者仍须由操作者确认已停止；不能把文件锁检查当成整台机器的进程清单。
   提交前重新核对 revision/digest；冲突则放弃旧预演并重新计算，不能覆盖并发修改。
   将校验通过的副本原子写入，权限保持私有，revision 单调递增，结构版本与迁移记录一起提交。
5. **切换和验证**：激活匹配程序，按原托管方式恢复原本运行的服务，保留主动停用状态。
   CLI 核对程序和健康，并通过本机令牌接口检查 Backend 核心域的 saved/applied revision 与摘要；
   其他消费者的配置生效、登录及任务保活由机器升级验收继续核对。
   只有配置写入成功或进程启动成功，均不能单独判定升级成功。
6. **记录结果**：持久记录事务标识、精确程序版本、源/目标配置版本、迁移步骤、备份位置、
   当前阶段及错误，不记录密钥值。重试先核对实际文件、程序指针和进程状态，再决定继续或恢复。

配置原子替换不等于整个升级是原子事务。配置提交前失败时，仅在原配置摘要和 active 指针均未变化时尝试恢复原服务，并记录恢复结果；
提交后启动失败或进程中断则保留恢复点，明确报告已提交到哪一步，不能承诺“失败一定自动回到旧服务”。

## 恢复与回退

正常流程只向目标版本迁移，不要求为每个步骤实现反向迁移。回退旧程序时核对它能够
读取的配置版本，必要时恢复该次升级的配套配置备份；恢复仍需身份核对、冲突检查及修订记录。
若升级后已有新配置修改，应先保存当前状态并展示将丢失的修改，不能自动覆盖。
旧程序不能直接加载它不认识的新结构，也不能让旧 supervisor 抢先启动。

配置恢复不代表数据库可恢复；数据库已有新写入或发生不可逆变化时，单独评估恢复条件，
不能用旧数据库覆盖新数据来凑出“回退成功”。无法安全回退时报告现状及可用的修复路径。

## 发行和验收要求

发布流程检查配置变化，交付匹配的版本声明、迁移代码和验收证据；升级流程执行这些确定的能力。
Skill 负责定位实例、调用工具、补齐缺失输入和解释结果，业务兼容正确性由程序保证。
两个入口见 [NPM Server 运维](./npm-server-operations.md)。

涉及配置演进的发行，在提升正式 channel 前至少覆盖：

- 新装、相邻版本升级、从声明支持的最旧配置跨版本升级；既有显式值、身份和路径保留。
- 旧默认行为保留、旧字段移除、目标结构校验通过，业务读取不依赖旧字段兼容分支。
- 重复执行无额外写入；未来版本、缺失凭据、迁移链缺口、坏文件及并发修改在切换前拒绝。
- 迁移提交前后中断及新版启动失败的恢复；CLI/Server 混合版本不会损坏共享配置。
- 匹配备份的配置回退、升级后再次编辑时拒绝静默覆盖，以及数据库恢复边界。
- 使用实际发行产物在隔离实例中启动，验证配置真正生效；新装健康检查不能代替旧配置迁移。

通用验收已接入现有 `pnpm server:verify-installed`，因此四平台发行构建会执行隔离 CLI
迁移链、冲突、拒绝运行中迁移、提交中断恢复、配套旧工具恢复及真实服务无配置变化更新。
范围见[配置升级验收计划](../testing/platform/configuration-upgrades.testplan.yaml)；合成版本不是正式配置版本。
每次新增具体迁移仍按[测试规范](../testing/README.md)补齐该变化的真实旧配置场景，不新增单元测试。
需要迁移却未交付执行能力，或相关验收未通过时，不宣称支持自动升级，不提升正式 channel。

## 添加下一次迁移

目标版本定义在 `packages/shared/src/configuration/compatibility.ts`；步骤集中追加到
[version-migrations.ts](../../packages/config-node/src/version-migrations.ts) 的注册表。
每一步声明稳定 `id`、`from`、`to`，域迁移另声明 `domain`；版本每次增加 1。
步骤编辑 YAML Document，保留无关字段和注释；metadata、版本及迁移记录由执行器统一提交，
步骤不能自行改写。当前没有需要变更结构的字段，因此注册表为空，不为测试制造正式版本号。
新增步骤时同时更新字段定义、目标版本和所有读取者，保证最终校验通过；新增可选字段不需要
转换时，可以不加步骤，但仍须验证原配置可直接使用。

配置恢复点写入 `<configRoot>/config-upgrade.json`，提交前记录 `prepared`、源摘要、预期结果摘要
和备份 ID，提交后记录 `committed`。若在配置 rename 后中断，重新预演并提交会按当前摘要
补齐回执，不重复修改配置。未知结果先核对该回执、实际 YAML 与 Server 的 `update.json`。
