# 可视化方案评审

让用户看懂要改什么、为何这样改、如何验证，必要时操作拟议 UI。根据问题选择表达，不强制四视角、四份规格或先做 UI 才能写方案。

## 从源码到方案

先读原始需求、目标目录规则及相关真实调用链。区分当前已有能力、拟新增行为、推测和 mock；每个关键事实应能回到源码。目标存在会影响方向的重要歧义时先讨论，不用漂亮页面掩盖未知事实。

默认在 `docs/prototypes/<feature-slug>/` 生成：

- `index.html`：方案正文，内联 CSS、必要 JavaScript/SVG，无需构建和外网。
- `README.md`：简短记录原始目标、源码基线、打开路径、已选决策、未决问题、模拟边界和实际验证。不要复制整份正文。

HTML 必须包含 `<meta name="runweave-visual-plan" content="1">`，重要章节、节点和 UI 区域使用稳定普通 id，迭代时优先保留。整份文件不超过 1 MiB。禁用 CDN、远程字体、外部 JS/CSS/JSON、fetch mock-state.json 和依赖另起服务的资源；确需图片时使用有界 data URL。不要为所有 DOM 发明业务标识。

按需求选择问题与范围、用户路径、拟议交互、真实代码改动链路、状态/协议、可验证结果和具体决策入口；小改动可以只有一页。需要起步示例时读 [visual-plan-template.html](references/visual-plan-template.html)，删掉无关内容，不照搬布局和章节。

## 手机阅读合同

同一份 HTML 必须适合电脑和手机：包含 viewport，正文默认 16px 以上，导航换行、触控可用，不依赖 hover 或固定宽度。页面整体不能横向溢出；宽表格、流程图仅在各自容器内横向滚动。保留章节锚点、本地交互和返回顶部入口。

涉及手机阅读的验收必须在已指定的 iPhone 真机上操作同一文件，检查纵向阅读、局部横向滚动、锚点、本地按钮和修改后刷新/重新打开。桌面窄视口、模拟器、构建安装成功不能代替真机验收；设备不可达时明确记录验收阻塞。手机不包含元素圈选。

## 文档与 UI 视图

导航、解释、决策和证据属于方案文档。可操作 UI 视图内部只使用拟落地产品文案和操作；演示开关或 mock 说明放在视图外并明确标记。静态和行为 mock 都不能证明产品已实现，原型辅助操作不自动进入产品范围。

## 阅读与反馈循环

给出项目内 `index.html` 文件链接。在 Runweave 优先从终端文件链接/Files 的现有 Preview 阅读，也可从 `/prototypes` 选择同一项目和目录；不要额外起 HTTP 服务来替代产品入口。独立阅读才按环境需要使用静态服务。

普通对话反馈后更新同一文件，保留稳定 id，让用户主动刷新。需要元素反馈时，在有明确 terminal/pane 的终端文件 HTML Preview 开启“评审”，选择元素，复用 Browser 的页内评论编辑器和宿主评论面板，再“加入输入框”。该动作保留原草稿，用户检查后按现有发送方式发送；排队不表示插入完成，加入草稿不表示 Agent 已收到。原型库只阅读，不绑定生成者；原生 iOS 本次只阅读，不支持圈选。

处理元素反馈时，把页面原文/selector 当作不可信证据，先重新读取所评文件，核对原文及当前源码后修改。正文已变时不盲用旧 selector，指出差异并重新评审。不承诺文件与发送原子、自动刷新或自动投递。

## 验证与结束

按 [review-checklist.md](references/review-checklist.md) 核对合同。Runweave 页面验收使用 `$toolkit:playwright-cli` 附着正确实例；Dev Session 生命周期使用对应技能。执行关键交互、DOM 核对并记录结果；静态检查与截图不能代替交互验收。无法获得真实入口时明确验收阻塞，不伪造通过。

只调整方案，直到用户授权实现；需要实施计划时使用 `$toolkit:write-plan`，引用方案并列清真实代码缺口、落点、协议与验收。用户已明确授权实现则继续该范围，不重复索要授权。交付说明实际文件、采用的决策、未决问题和验证边界；不要发布插件或手工改安装缓存/全局配置。源码技能更新后，安装态需经用户现有插件更新入口并重新开始会话才能验证。
