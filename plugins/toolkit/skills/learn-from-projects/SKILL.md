# 从外部项目学什么

用户问“有什么值得学”时，先弄清材料里哪个做法可能改变用户做事的方式。既看已有功能能否改进，也留意当前项目还做不到的事。用户点名想了解某个行为时，先把那个行为讲明白。

## 回看以前怎么做的

用来源名称、功能名或用户动作找相关的旧调研、原始对话、任务记录或运行数据。沿时间读到后续追问和实际处理结果：当时推荐了什么，用户纠正了哪个前提，最后采用、搁置或验证了什么。摘要用来定位；关键判断回到原对话、原始数据或对应改动核对。历史中没有后续结果时，保留这个未知。

用历史提出要核实的问题，再对照当前版本和实际用法。建议优先改某个问题时，看看它在一段明确的时间里发生了几次、影响了谁、花了多少时间。同一任务反复受阻与多个用户各受阻一次，含义不同。新能力还没有使用记录时，可以查用户过去怎样绕路完成同一件事。查不到相关历史，就交代查过哪里，以及哪条判断还缺依据。

## 从材料追到机制

找到最能说明做法的一手材料，例如设计文档的具体段落、实现入口、实验设置。文章同时讲产品本体和第三方扩展时，追到实际产生行为的组件。用一次具体操作解释谁触发、谁处理、用户会看到什么。如果读到的是宣传或作者自述，写明依据的性质。引用性能或效果数字时交代基线、工作负载和指标口径。

## 核对实际效果

已有功能先选一个用户在意的结果，例如同一任务能否办完、需要几次人工补救。用已确认的启用时间划分前后，取同一入口的完整记录，保留失败、接管和缺失结果。对下面的记录可直接运行 [compare_history.py](scripts/compare_history.py)，由脚本计数并列出每次观测的来源。它比较两个等长的半开时间段，分界时刻属于后一段。定时任务按计划触发时间分组，已知跨过上线时刻的执行单列。

```sh
python3 scripts/compare_history.py --scheduled-db "$db" --task-id "$task" --cutover "$enabled_at" --days 7
```

从本技能目录运行。上例只读 Runweave 运行库，只取同一任务的自动调度。其他项目可用 `--events history.jsonl` 替换数据库和任务参数，每行导出一个同类事件，保留原记录的 `id`、带时区的 `at`、原始 `outcome` 和可定位到原件的 `evidence`。缺失结果用 null。会话需保留会话及轮次或事件位置，按同一种可观察结果提取。只有自然语言自述时，标明“报告成功”。

顺着一条改变判断的记录，查当次会话和独立回执、产物或操作前后快照，确认新能力确实参与、用户得到什么结果。有反例就查看反例。说明期间任务要求、负载或版本变化。只有历史分布变化时，报告观察值，把单项改动的贡献留作未知。没有后段数据时只交付基线；没有记录的窗口不能算作零次失败。

方案还没上线但有相似历史输入时，用同一批真实案例回放旧做法和候选做法，比较用户在意的结果，把数字标为回放结果。全新功能可以先交付一次真实试用：谁为哪件事用了它、是否做成、有何代价。积累可比记录后再谈改善幅度。

## 回到当前项目

从本项目里同一个用户动作、数据流或故障场景入手，沿实际入口查看相关实现、配置、已有数据或历史尝试。给出可回查的位置。判断现有能力已经覆盖了什么、还有哪一处差异会影响用户。缺少运行数据时，只把代码能证明的部分作为事实。

逐项判断哪些机制值得迁移，以及为适应本项目必须改变什么。优先复用已有能力。对值得尝试的做法，指出一个具体落点、预期变化、主要代价，以及哪项观察会支持采用或让人放弃。外部和本地证据已经足以否定建议时，到此结束。只缺一项关键事实时，指出获得它的最小调查或对照实验。

## 给用户的结论

先用用户熟悉的场景讲清楚值得学什么、学了会有什么变化。挑与这次问题有关的发现；一个说得清楚的例子就可以交付。给出实施优先级时，把最影响排序的历史事实和当前项目依据放在结论旁。后续证据改变原建议时，点明是哪条事实改变了判断。调研可以只带来理解，也可以得出维持现状的结论。用户同时要求实施时，再按其授权推进。
