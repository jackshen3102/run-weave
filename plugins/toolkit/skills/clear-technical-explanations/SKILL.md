# 简化技术表达（ASD-STE100 启发）

改写难懂或有歧义的技术文本，让读者无需询问作者也能准确理解。保留原文语言，除非用户要求翻译。目标是消除歧义，不是把文字压到最短。

## 两种模式

改写前选择模式。用户未指定时，按文本类型判断。默认不宣布模式。

- **Strict**：操作步骤、错误信息、工具描述、Agent 间指令和误读成本高的文本。严格保持同一术语对应同一含义，一个句子只表达一个指令，执行适用的结构规则。
- **STE-flavored**：README、PR 描述、变更记录和解释性文章。执行结构规则，词汇规则作为建议，不为了统一词汇抹掉文章的必要语气和表达。

这两种模式都必须保留事实、条件、范围、例外、数字和不确定性。

## 核心改写规则

### 结构规则

| 规则               | 做法                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 主动表达           | 明确谁执行什么动作。主体确实未知或无关时，不为改成主动句而虚构主体。                                                         |
| 一个句子一个指令   | 将连续操作拆为独立句子或步骤。条件必须紧邻它限定的动作。                                                                     |
| 短句               | 英文操作句不超过 20 词，描述句不超过 25 词。中文按独立动作或判断拆句，不机械套用英文词数或另定字数上限。必要精度优先于句长。 |
| 拆开分号连接的内容 | 用独立句子或步骤表达多个判断。破折号不一概禁用，但检查它是否把多个判断挤在一起。                                             |
| 拆开长串名词       | 英文避免超过 3 词的名词堆叠。中文明确长串名词之间的关系，不强行套英文词数。固定术语和标识符保留原样。                        |
| 不省略必要成分     | 保留读者需要的主体、动作、对象和限定。中文零主语自然且指代唯一时可以保留；有多个可能主体时明确指代。                         |
| 保留确定程度       | “可能失败”不能改成“失败”，“可能由 X 引起”不能改成“由 X 引起”。                                                               |
| 段落聚焦           | 每段只讨论一个主题，通常不超过 6 句。                                                                                        |
| 步骤和条件用列表   | 3 个以上步骤或条件优先使用列表，明确先后关系及各条件对应的动作。                                                             |
| 避免模糊短语       | 英文优先用明确的单词动词替代多义短语动词；中文把“处理一下”等模糊动作改明确，但不得猜测原文未说明的动作。                     |

### 词汇规则

优先使用常见、含义明确的词。Strict 模式保持同一动作和对象的名称一致；STE-flavored 模式允许不引起歧义的自然表达。

- 同一概念不要交替使用多个名称，让读者误以为它们是不同对象。
- 使用动词表达动作，例如将“进行分析”改为“分析”。名称本身是技术术语时保留。
- 保留必要的领域术语。陌生术语可以补一行释义，但不改写 API、命令、文件路径或标识符。
- 不机械将英文“一词一种词性”规则套到中文。判断依据是含义和指代是否明确。

此技能不包含 ASD 官方词典。词汇选择是消歧建议，不是正式批准词校验，也不能据此保证 ASD-STE100 合规。

### 时态与状态

英文优先使用简单时态，但复合形式承载当前状态或不确定性时保留。例如不能把“may have failed”改成已确认失败。

中文保留“已”“正在”“将”“尚未”等状态信息，以及“可能”“仅当”“至少”“最多”等限定。不为句子变短而删除它们。

## 扫描清单

逐句检查这些常见问题：

1. **名称轮换**：同一对象被称为“用户”“客户”“客户端”，但没有说明是否是同一主体。
2. **套话和限定堆叠**：删除“值得注意的是”等无信息表达，保留真正表达置信度、频率或条件的限定。
3. **动作名词化**：用明确动词替代“进行……的处理”等绕法。
4. **营销形容词**：删除无依据的质量夸赞，或使用原文已有的可核对数据。不能补造数据。
5. **长句串联**：多个判断挤在一个句子里，需要按逻辑拆分。
6. **模糊动作短语**：明确原文已经给出的动作；原文没有足够信息时指出歧义，不代替作者决定。

## 改写流程

1. 选择 Strict 或 STE-flavored 模式。
2. 先读完整原文，确定改写后必须保留的意思。
3. 逐句检查结构、词汇和扫描清单中的问题。STE-flavored 模式不强制统一所有自然用词。
4. 改写有问题的句子，保留原文的事实、条件、范围、数值、单位、先后关系和确定程度。原文未陈述的原因、频率或机制不能补入。
5. 对照原文核对语义。若简化会丢失精度，就保留较长表述，并按下方格式说明。
6. 返回结果。原文已经清楚时保留原文，不为了产生改动而重写。

词数、标点等结构检查不能证明改写保留了语义。

## 输出格式

**默认只输出改写后的文本。** 不加开场说明、模式名称、问题计数、改动总结、规则清单或结尾邀请。

若刻意保留某个无法安全简化的表述，可以在正文后加一行：

> 保留原表述：〔表述〕。进一步简化会丢失〔必要信息〕。

没有需要说明的保留项时，不加这一行。

用户要求“展示差异”“解释修改”或“列出规则”时，改为输出比较表：

| 规则         | 原文                         | 改写                       |
| ------------ | ---------------------------- | -------------------------- |
| 动作名词化   | 请对日志进行分析。           | 请分析日志。               |
| 保留不确定性 | 请求可能由于旧客户端而失败。 | 旧客户端可能导致请求失败。 |

表后注明模式；有意保留的内容及理由用一行说明。

## 边界

只改善表达，不改变文本所描述的行为，不把缺乏依据的内容变成事实。保留所有条件、例外和不确定性；不能为了更短而降低精度。

创意、营销或以语气和说服为目标的文字不适用此技能。没有实质内容的段落，不能仅靠改写变得有用。
