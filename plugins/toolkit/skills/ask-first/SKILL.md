# Ask First

先探索，再对齐，后执行。提前识别做错后返工成本高的决策，让用户判断真正需要
拍板的取舍；代码能回答的事实和低风险细节由 Agent 自行处理。

本技能用于任务启动前的关键决策对齐，不替代完整设计流程，不强制生成设计文档、
实现计划、术语表或 ADR，也不把所有工作变成审批流程。

## 先判断是否需要对齐

读取用户当前要求、已有确认、仓库指引和相关上下文。识别尚未解决且会改变结果的
歧义，例如数据冲突策略、接口兼容、核心抽象、异常处理、产品行为或验收边界。

- 用户已经选定方案或授权 Agent 决策时，沿用该授权，不重新询问已解决的问题。
- 一行命令、规范明确的小修、纯查询或没有重要歧义的任务直接执行。
- 用户明确要求只讨论、先对齐时，保持只读；关键歧义解决前不进入依赖它的实现、
  文件修改或其他有副作用的操作。独立且已授权的工作可以继续。

## 阶段一：探索事实

先看相关代码、文档、配置、调用方和验证入口，再提问。探索深度与任务复杂度相称，
不要为凑齐维度扫描整个仓库，也不要把同类模块的做法当作必然正确的答案。

复杂且可拆分的任务，在运行环境允许委派时使用子 Agent 并行只读探索。主 Agent
按实际链路划分独立范围，可从实现者、调用方、维护者或权限边界等视角切入；
小项目或单一链路由主 Agent 自查，不强制固定人数或角色。

给每个子 Agent 明确目标、范围和证据要求：

- 只收集事实、指出矛盾和风险，不修改文件、不替用户决定方案。
- 返回简短事实清单，每条附文件路径和必要行号或来源，区分事实与推测。
- 标注未覆盖范围和缺失信息，不返回整段代码或大批原始工具输出。

主 Agent 汇总并核对关键证据。结果冲突时先检查是否来自不同版本、运行时或作用域；
能通过继续读取解决的冲突自行解决。仍涉及产品或范围取舍时才呈现给用户。
子 Agent 不可用、超时或证据不足时改为自行探索；未补齐的信息如实说明。

## 阶段二：筛选与提问

将发现分为三类：

1. 代码、合同或用户指令已有明确答案：自行采用。
2. 影响小、容易撤销的细节：选择符合项目现状的合理默认值。
3. 多个合理选项各有代价，且选择会改变方案、范围、风险或验收：与用户对齐。

值得询问的问题应同时具备项目依据、真实取舍、执行影响、推荐答案，以及可验证的
结果。不要问 Agent 自己能查明的事实，不捏造覆盖率等数字，不把测试示例当作新增
测试的授权；遵循项目现有验证规则。

按依赖关系和返工成本排序，先解决上游决策。通常一次只问一个关键问题；互不依赖
且容易一起判断的问题可以合并。每个问题简洁给出：

> 问题：一个会改变结果的具体选择。
> 项目依据：相关代码、文档或配置事实。
> 推荐：建议选项及理由，包括主要代价。
> 其他选择：真正可行的替代方案及影响。

根据回答更新剩余决策，不重复已确认内容。用户说“你决定”即授权 Agent 选择；
用户要求“直接做”时，按已有范围推进合理方案，只保留确实缺少必要信息或授权的
问题，不另设一轮审批。用户说法与现状冲突时，说明证据；用户明确的新目标可以
改变旧行为，不能用历史实现替代本次要求。

## 收口与执行

关键取舍解决后，给出简短共识摘要：目标、改动范围、关键决策、验收依据，以及会
影响执行的未决问题或默认处理。不要机械填充所有栏目。

用户要求先确认再执行时，展示具体方案后等待确认；已有明确执行授权则直接进入
执行，不重复审批。没有需要用户判断的问题时，不为启动任务制造问题或共识门禁。
用户另有要求时再落盘计划或设计文档，沿用项目现有文档体系。

交付时如实区分已实现、已验证和仍有局限的部分。探索中发现的范围外问题可以指出，
不因“根治”或“完美交付”擅自扩大任务。
