# Code-Grounded Requirements

先明确哪项项目事实会影响回答或修改。涉及行为变更时，对齐当前行为、用户目标和两者的差异。

## 触发边界

- 解释一次实际行为、判断某项限制是否应保留，或确定修改会影响哪些调用方时，若结论取决于尚未确认的项目事实，就针对该事实取证。
- 已有证据足以回答问题，或用户已指明唯一位置和具体改法且没有待核实的依赖时，直接回答或修改。

## 硬规则

- 解释一次实际行为时，查当次生效的实现、配置或运行记录。
- 判断某项限制是否应保留时，对照用户要求或适用契约。
- 证据足以回答当前问题就停。仍有会改变结论的缺口，或不同证据支持相互冲突的结论时，再沿相关调用链追查。
- 关键判断：能力是**已存在但链路没接上（接线/回归问题）**，还是**真的缺能力**——别把前者误判为后者。
- 需求对齐前不进入实现。建议可以给，但必须基于代码现状。

## 证据标准

- 给出直接支撑结论的证据位置，例如运行记录、配置项、实现位置或契约条款。证据只解释了当次行为时，结论就限于当次行为。
- 标明推测及其依据，指出仍会影响结论的未知事实。

## 输出格式

按下面顺序，按需裁剪：

### 当前现状

说明证据确认了什么，并给出对应位置。

### 需求理解

用更精确的话重述目标，点明这次改的是行为 / 存储 / UI / 路由还是接口。

### 差异与影响

现状和目标差在哪（行为、数据模型、存储语义、权限、路由跳转），以及可能受影响的模块。

### 建议

1 个推荐方向（必要时补 1 个备选），每条说明为什么贴合当前代码——是最小修复还是结构性改造、是否复用已有接口/组件。

### 待确认点

只在确实需要时保留，1-3 个高价值边界问题；能从代码看出来的不要反问。

默认用中文回复。
