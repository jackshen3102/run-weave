# 编写实施计划

核心原则：

> **让执行者在实现方式上有空间，但不要让它在需求理解、边界和验收标准上有空间。**

计划要写清执行者不能猜的内容：目标、边界、约束、文件范围、接口、验证方式、验收标准、不做什么。它不是逐行代码生成器。

## 使用边界

适用：已有明确需求/目标，需要多步完成，且尚未进入实现（或用户要求先计划）。

不适用：

- 需求不清、连「做成什么样才算对」都判断不了 → 先补 spec 或提澄清问题；
- 单文件、低风险、几分钟能搞定的小修；
- 用户只要脑暴或开放式设计方向，不需要落地计划。

## 流程

1. **先查上下文。** 在已有代码库里写计划前，先读相关代码、文档、配置、测试，除非用户明确要求只基于需求草案。
2. **定范围。** 需求跨多个独立子系统时，拆成多个可独立验证的计划。
3. **选粒度。** 按风险选 L1/L2/L3，不要所有任务都顶格写。
4. **必须落盘。** 计划完成后保存为本地 Markdown 文件：用户指定路径则用指定路径；否则存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`，目录不存在先创建。
5. **回复给路径。** 最终回复必须包含计划文件路径；本轮配套编写或更新了测试计划时，一并给出其路径和格式校验结果。仅在用户没说下一步时，简要给出执行方式建议。

## 计划粒度

按风险选择，不要过度精细：

- **L1 方向性**（低风险、执行者熟悉代码库）：目标、文件/模块范围、关键约束、验收与验证方式。不强制给代码。
- **L2 结构化**（中等复杂、多文件、需设计接口、交给 agent 执行）：任务拆分、精确文件路径、关键接口/类型、关键验收场景、验证命令、风险点。关键/易误解逻辑给代码，普通 glue code 引用现有模式。
- **L3 执行级**（高风险：认证/权限/支付/数据迁移/并发/跨平台/弱模型执行）：细粒度 checkbox 步骤、精确文件路径、关键或完整代码、精确命令与预期输出、逐任务验收清单、提交方式。

## 每个计划必须写清

- 目标、非目标（不做什么）；
- 用户可见行为、输入输出、业务规则；
- API 合约、数据结构、权限/安全边界、错误处理、兼容/迁移/回滚；
- 修改或新建的文件路径及各自职责；
- 验收标准 + 验证方式（命令/操作 + 预期输出 + 失败判断）；
- 高风险点：是否可能造成数据丢失、安全风险或线上回归。

业务逻辑、数据转换、权限、状态机优先给自动化验证；UI、配置、文档、一次性脚本可用手动验证清单。

## 按需配套测试计划

- 每份实施计划都要有验收标准和验证方式，但不默认新增 YAML 测试计划。现有检查足以覆盖的低风险改动，在实施计划里写清验证命令、操作及预期结果即可。
- 用户要求配套测试计划，或写计划时发现验收需要独立、可逐条执行的用例（例如交给 Agent Team 执行，或关键状态、权限、恢复行为缺少覆盖），应检查已有 `docs/testing/**/*.testplan.yaml`，判断是否需要新增或更新；不能仅因计划属于 L2/L3、跨文件或涉及实现就强制生成。
- 需要新增或更新时，在本轮自动调用 `$toolkit:write-test-cases` 一起完成，无需用户再次点名或确认；不要只在实施计划中留下“后续补测试计划”的任务。用户明确要求不生成测试资产时遵循该范围，并写清替代验证方式与覆盖缺口。
- 已有用例足够时直接引用；需要补充时优先更新同主题计划，避免重复。新增或重写仍只使用 `docs/testing/**/*.testplan.yaml`，遵循项目格式并运行 `pnpm testplan:validate <路径>`，在实施计划的验收章节引用对应路径。
- 联动只负责编写与格式校验，不自动执行用例。执行阶段按任务授权使用 `$toolkit:run-test-cases`；格式校验通过不代表行为验收通过。

## 可以留给执行者

内部 helper 拆分、局部命名、非关键 glue code、与现有风格对齐的低风险实现。前提：目标、约束、文件位置、验收标准已明确。

## 落盘前自查

- 每个需求都对应到任务或非目标；
- 没有无法执行的占位（TBD/TODO、「加适当的错误处理」、「处理边界情况」等含糊表达）；
- 引用的类型/函数/字段/路径前后一致，且前文已定义；
- 粒度匹配风险，每个任务都有可执行的验证方式；
- 若本轮需要配套测试计划，已完成编写或更新、路径引用和格式校验；已有用例足够时已引用，无需新增时不强制创建；
- 文件已写入计划路径。

!!! 必须使用中文编写计划文档
