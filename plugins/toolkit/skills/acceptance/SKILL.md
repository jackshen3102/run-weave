# 验收

从本轮用户要求决定工作范围。实现任务的验收由主 Agent 负责到最终结果；用户只要求验证时，执行检查并报告事实。仅要求“用这组截图做图册”等材料制作时，直接进入[材料流程](references/materials.md)，按已有证据说明覆盖范围。

## 对照原目标

读取用户采纳的计划、口头约定和后续修订，沿用指定步骤、设备、环境和交付物。依据[目标与证据](references/criteria.md)逐项核对。多项承诺可用小表列出“约定、实际结果、证据”，简单改动用一句结论和对应证据即可。用户指定的步骤若有偏离，说明差异及影响。

执行前把每项承诺写成可以由观察回答的问题。按下列顺序选择验证方式，普通小改动在回复里给出结果与对应证据即可。

1. **用户要证明什么？** 明确在什么入口、对哪个对象做什么、预期观察到什么。一个需求可以有多个判断问题，按实际承诺选择。[证据选择与例子](references/evidence-selection.md)给出常见问题和合适的交付形式；未列举的需求也从其可观察结果推导证据。
2. **这类改动容易漏掉什么？** 对照本次真实影响范围补充检查。例如修复共享规则要核对相关调用方，性能优化要检查收益和代价。已有证据能支持多个判断时直接复用。
3. **多步任务走到了哪里？** 若跨步骤、异步或跨端，沿同一对象关联触发、交接和用户终态。标出最后一个有证据的节点、它证明的事实和下一项待执行的动作。按原授权继续，直到取得终态证据或满足受阻判定。

已有 YAML 用例交给 `run-test-cases`，浏览器用 `playwright-cli`，原生 iOS 用 `agent-device`。

在已有实现或修复授权内，保留失败证据，恢复环境或修复范围内问题，重跑原场景，再完成剩余承诺。某次用例运行停止、Review 返回或构建成功时，回到原目标判断还有哪些工作。只读评审沿用 Reviewer 权限。

验收执行或材料制作遇到障碍时，按[受阻判定](references/criteria.md#受阻判定)处理。对同一障碍至少实际尝试 5 种不同解决方案且全部失败，才可报告该项受阻。

## 选择交付形式

直接在回复中给结论、图表或可打开的证据。需要手机图册、视频或原始录屏时走[制作与交付](references/materials.md)。主观风格用实装画面和约定参考交给用户判断。最终说明各项已验证、失败或阻塞到哪一步；制作材料、提交代码和发布各沿用本次授权。
