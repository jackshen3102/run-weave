# 从用户问题选择验收证据

## 以承诺决定实际观察点

下表用于举例。多个问题可以组合，新的问题只要能从约定导出可观察的终态，就沿同样的方法取证。

| 用户要判断什么                         | 实际观察点                                                                                                       | 合适的呈现                                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 看起来对吗，操作过程符合预期吗？       | 在指定端查看代表性数据；对“只读”等交互承诺核对实际控件行为。风格按用户采纳的参考对照                             | 一张带上下文的截图；风格用并排图，动作或等待顺序重要时用短视频                               |
| 操作真正完成了吗？                     | 从用户入口执行到业务终态。要求保存时，退出后重新打开同一条记录，读回保存值                                       | 关键操作与终态回读；复杂交接补流程图                                                         |
| 数据正确、完整且无重复吗？             | 用可核对的输入对照输出、数量、关键字段和实际副作用。例如报价和账单各自读出 3 × 5 的金额                          | 预期与实际对照表，附关键回执                                                                 |
| 谁能做，谁应被拒绝？                   | 用获准的代表性角色操作正常入口，核对允许或拒绝后的最终状态。编辑按钮隐藏只覆盖界面                               | 角色、动作、结果、数据回读对照                                                               |
| 中断后还能继续吗？                     | 从中断前跟踪同一任务到恢复后首次成功的业务操作，核对人工介入、丢失或重复                                         | 带事件证据的时间线，若用户关注视觉过程则附短视频                                             |
| 快多少，谁受益，付出什么代价？         | 在可比设备、负载和冷暖状态下核对结果正确性，记录前后值、单位、样本数和波动。选与优化机制有关的成本，例如缓存峰值 | 用典型操作给出绝对差和适用时的相对变化，多档规模可用曲线。缺可比基线时仅报告当前值和缺失条件 |
| 谁受影响，相邻功能和历史数据还可用吗？ | 找到共享逻辑的真实调用方，复测相关入口或旧数据，区分实测结果、可能风险与覆盖缺口                                 | 影响范围与回归结果小表。兼容性可按版本列出代表性记录的前后值                                 |
| 指定环境已交付可用吗？                 | 核对目标环境、版本或设备身份，从该环境的用户入口完成约定动作                                                     | 版本回执和实际终态，区分构建、安装、启动与真实操作的证据                                     |

## 按工作类型检查遗漏

Bug 修复从原症状出发，在可比条件下复测，并检查可能受同一改动牵连的入口。优化关注基线和资源权衡；数据迁移关注旧值及缺失字段；部署关注实际运行版本；重构关注现有调用者的行为。只补充有用户承诺或真实改动依据的项。

## 跨步骤时串起同一对象

例如用户要求“导出大文件，断线重连后还能下载”。沿同一个导出任务核对 **提交 → 启动 → 断线 → 重连 → 找回原任务 → 下载并打开文件**。只有启动回执时，报告已启动并继续验证恢复和下载；只有重连记录时，还需要核对任务身份。将下载结果与约定的文件内容关联后，才能确认这一承诺。节点来自真实步骤，图示关联原始记录，尚未执行的节点明确标注。

**历史例子。** iOS 工作区 diff 曾把三行修改显示成整份文件重写。同一份 2,000 行输入，只改第 101、1,001、1,901 行，修复前显示 2,000 删、2,000 增，修复后为 3 删、3 增。数字回答算法是否修对，模拟器截图回答用户能否读懂行号与折叠。两份证据各有用途，这些计数衡量显示正确性。若任务还承诺“大文件打开更快”，则另需测量同一文件打开到可交互的耗时。

普通交付可直接在回复中附截图、Mermaid 图或证据链接。需要手机图册或视频时，复用现有制作和预览脚本。图册已有 v2 的预期、实际、结果、证据页字段，可直接复用。流程图可直接放在回复里，避免把示意图计作图册里的实测页面。
